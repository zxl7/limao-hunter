## 1. 客户与推送台账模块（重新设计·核心变更）

### 1.1 定位变化

| 维度 | v1 设想 | v2 定稿 |
|---|---|---|
| 本质 | 面向客户的权限与订阅系统 | **内部台账 + 推送调用** |
| 客户怎么用 | 登录 / 访问专属 URL | **在群里收卡片**（可选升级：看门户页） |
| 鉴权 | JWT + token 签发 | **无**（内部模块，不对外暴露） |
| 计量 | 访问日志 + 会话 | **推送日志**（谁在何时收到哪张卡、成功/失败） |
| 数据结构 | 5 张表（含订阅关系、访问计量） | **4 张表**（客户 / 通道 / 规则 / 日志） |
| 迁移成本 | 需重写 client_mirror | **语义零变更**，仅把 settings.json 的 `rules` 搬进表 |

**关键保留**：现有 `client_mirror` 的三组匹配语义（`card_patterns` / `title_patterns` / `exclude_patterns`）与「测试群一律不镜像」硬门、「失败只记 audit 不阻断主流程」策略，**全部原样继承**。这不是重写，是**载体升级**。

**实测验证（`scripts/push_card.py`，465 行）** —— 台账化的改动面比预期更小：

| 现有函数 | 现状 | 台账化改动 |
|---|---|---|
| `load_mirror_config()` | 读 `settings.json` 的 `client_mirror` | **替换为读台账**（唯一需要改的函数） |
| `mirror_targets(card_name, source_key, card)` | 四类命中：`channels` / `card_patterns` / `title_patterns` / `prod_card_patterns`，含硬门 + 自指跳过 + `exclude` | **一行不改**（入参恰好就是 `resolve` 的入参） |
| `mirror_push(card, targets, card_path)` | 逐目标推送 + 逐目标 audit | 增加一次 `push_logs` 写入 |
| `main()` 调用点 | 主群 push 成功后才调 `mirror_push` | **一行不改** |

→ **迁移成本 = 替换 1 个配置读取函数 + 增加 1 处日志写入。** 附带可直接复用的既成能力：
- 选群策略（`--webhook` > `FEISHU_PUSH_ENV` > 交易日自动）
- 同内容幂等去重（10 分钟窗口，`cache/push_dedup.json`）
- 推送前质量门（lint + schema 不过即阻断，`--skip-lint` 兜底）
- 失败自动告警到测试群（`_notify_failure`）
- append-only 审计（`common/audit_log.audit`）


### 1.2 表结构（4 张）

```
clients                       客户主档
  id            bigserial PK
  name          text          客户名（如"蒋坤阳"）
  alias         text          简称，用于台账检索（唯一）
  tier          text          standard | custom      ← 对应 §3 的定制档
  status        text          active | paused | expired
  note          text          备注
  created_at    timestamptz
  expires_at    timestamptz NULL

client_channels               交付通道（一客户可多通道）
  id            bigserial PK
  client_id     bigint FK
  type          text          feishu_webhook | wecom_webhook | web_url
  target        text          webhook 地址 或 页面地址
  label         text          "客户群A"
  enabled       bool          ← 替代现有 enabled=false 一键全关
  secret_ref    text          密钥引用（不落明文）

client_rules                  订阅规则 = 现有 client_mirror.rules 的等价物
  id                bigserial PK
  client_id         bigint FK
  card_patterns     text[]      卡文件名含任一子串
  title_patterns    text[]      卡标题含任一子串   ← 跨 AI 拼卡最稳的匹配方式
  exclude_patterns  text[]      永久排除（如 gangtise_*）
  modules           text[]      模块白名单（V1..V6 或 M1..M7）
  priority          int         多规则命中时的优先级

push_logs                     推送日志（台账的"记录"能力）
  id            bigserial PK
  client_id     bigint
  channel_id    bigint
  card_type     text          short_spirit | snapshot | review | ...
  title         text
  ts            timestamptz
  result        text          ok | failed | skipped
  error_code    text          如 19001（webhook 失效）
  msg_id        text          飞书返回的消息 ID
```

**设计要点**：
- 只用了 4 张表，删掉了 v1 的 `content_packs`（并入 `client_rules.modules`）与 `client_subscriptions`（并入 `clients.expires_at` + `tier`）。
- `modules` 字段是**为门户预留的**：现阶段只用 `card_patterns` 决定"推什么卡"，将来若客户要看网页，直接复用同一份白名单渲染内容包，**无需改数据模型**。

### 1.3 调用时序（"调用"能力）

```
[tasks / scripts / pipeline]
        │
        ▼
  push_card.push(card, webhook=主群)
        │
        ├─ ① 推主群 ──────────── 现有逻辑完全不变
        │
        └─ ② 主群成功后 → cluster_ledger.resolve(card)      ← 台账被"调用"
                            │
                            ├─ 硬门：来源为测试群 → 直接返回空（不镜像）
                            ├─ 查 client_rules：card_patterns / title_patterns 命中
                            ├─ 减去 exclude_patterns
                            └─ 返回 [(client, channel)...]
                                    │
                                    └─ ③ 逐客户镜像推送
                                            └─ ④ 写 push_logs（含失败码）

  ⛔ 失败只记日志，绝不阻断主流程（沿用现有策略）
```

**接口契约（供 push_card 调用）**：

```
POST /api/v1/clients/resolve
  入参：{ card_file, title, source_webhook }
  出参：{ targets: [ { client_id, client_name, channel_id, channel_type, target } ] }
```

**为什么用 POST 而非 GET**：`resolve` 语义上是"按当前卡片的匹配规则求值"，且将来可能携带上下文（时段、市场），用 POST 便于扩展；同时避免被当作公开查询接口缓存。

**降级设计**：台账服务不可用时，`resolve` 返回空集 + 写一条 audit —— 行为等价于"没有客户要镜像"，**不会导致主群推送失败**。这与现有 `client_mirror` 的容错姿态一致。

### 1.4 交付三档（同一套架构，客户可选）

| 档 | 客户拿到什么 | 台账里的表达 | 适用 | 改动成本 |
|---|---|---|---|---|
| **A · 推送服务**（基线） | 群里收卡片 | `channels.type = feishu_webhook` | 绝大多数客户 | 零（现状即是） |
| **B · 门户访问** | 一个网页地址看内容 | `channels.type = web_url` + `rules.modules` 决定可见模块 | 想"看盘"的客户 | 中（需门户按内容包渲染） |
| **C · 私有部署** | 整套系统（Docker Compose） | `tier = custom` + 部署清单 | 数据不出内网的企业 | 高（一次性） |

**推荐**：以 **A 档为产品基线**（成本最低、与现有能力无缝衔接），B 档作为**同一架构下的可选升级**，C 档按项目评估。三档**共用同一份客户台账**，不产生分叉。

## 2. 部署：本地先行 → 服务器迁移

### 2.1 三阶段路径

| 阶段 | 运行位置 | 数据 | 前端 | 验收标准 |
|---|---|---|---|---|
| **S0 · 本地开发态** | 本机直接跑（Python venv + Node dev） | 沿用 `cache/*.json`（**只读**） | `vite dev` :5173 | 新模块跑通，**旧链路零影响**（现有 launchd 照常运行） |
| **S1 · 本地容器一体化** | 本机 Docker Compose（PG + Redis + API + Web + worker） | `cache` → PG **双写**，读逐步切 | Nginx 静态 + 反代 | 容器内全链路可用；双写一致性校验通过 |
| **S2 · 服务器迁移** | 云服务器（同一份 compose） | PG dump/restore | 可选 CDN / Pages | 域名 + HTTPS 上线；兜底通道保留 |

**核心原则：S1 与 S2 使用同一份 `docker-compose.yml`** —— 本机就是"缩小的服务器"。这样迁移动作退化为：换机器 → 拉代码 → `.env` 改 3 个值 → 起容器。**不允许出现"本地一套跑法、服务器一套跑法"**。

**S0 阶段的兼容要求**：新旧系统**并存**。现有 launchd 双守护 + 飞书推送链路在 S0 期间完全不动；新模块以"旁观者"身份读 `cache/` 数据，验证正确性后再进入 S1 接管。

### 2.2 十条「不得绑死本机」前置约束

这是本地先行的**最大风险点**——现有代码库有大量硬编码，若不预先治理，S2 迁移会变成重写。以下 10 条在 S0 阶段就要落地：

| # | 约束 | 现状问题 | 目标形态 |
|---|---|---|---|
| 1 | **路径全部配置化** | `ROOT / "cache" / ...` 遍布全库 | 统一 `Settings` 类从 `.env` 读取根路径 |
| 2 | **数据访问走 Repository** | 脚本直接 `json.load(open(...))` | 仓储层封装，可切 JSON / SQLite / PG |
| 3 | **调度抽象为 worker** | 逻辑写在 launchd 触发的脚本里 | `worker` 入口，本地 launchd 与服务器 cron 跑同一份代码 |
| 4 | **密钥全走 .env** | 已有 `wealth_code/.env`（好范例） | 全部密钥统一 .env + `.env.example` |
| 5 | **时区与交易日历显式声明** | 依赖本机系统时区 | 容器内显式 `TZ=Asia/Shanghai`，日历自持 |
| 6 | **日志输出到 stdout** | 现有落文件 | stdout 为主（容器友好），保留 `logging_setup.py` 的格式规范 |
| 7 | **产物路径可配置** | `cache/` 硬编码 | `DATA_DIR` 环境变量，容器内挂载卷 |
| 8 | **前端 API baseURL 注入** | 可能写死 localhost | 构建期/运行期环境变量注入 |
| 9 | **依赖锁定** | `requirements.txt` / `pnpm-lock.yaml` 已有 | 保持；容器构建可复现 |
| 10 | **冷启动演练** | — | 删空容器卷 → 一条命令起 → 全链路可用（**迁移前必做**） |

> 第 10 条是验收动作：不做这一步，迁移当天必然踩坑。

### 2.3 同构部署拓扑（S1 / S2 相同）

```
        ┌──────────────────────────────────────────────┐
        │              Nginx（HTTPS · 静态 · 反代）      │
        └───────┬──────────────────────────┬───────────┘
                ▼                          ▼
        ┌───────────────┐          ┌───────────────┐
        │  门户 Web      │          │  FastAPI API  │
        │  (静态 dist)   │          │  + WS 通道     │
        └───────────────┘          └───────┬───────┘
                                           │

                  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
                  │ PostgreSQL  │  │   Redis     │  │  worker     │
                  │  (主库)     │  │  (缓存/去重) │  │  (采集·计算) │
                  └─────────────┘  └─────────────┘  └──────┬──────┘
                                                           ▼
                                                  外部数据源（东财/选股宝/
                                                  同花顺/必盈/腾讯）

        ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄
```

## 3. 产品化与定制机制

### 3.1 产品基线 vs 定制点

```
┌─────────────────────────────────────────────────────────┐
│  产品基线（标准版）—— 一份代码，全部客户共享               │
│  · V1 看盘 / V2 复盘 / V3 异动 / V4 财富密码 / V5 查询    │
│  · 默认主题 · 默认阈值 · 默认标的池 · 默认推送时段         │
└──────────────────────────┬──────────────────────────────┘
                           │  只通过配置层差异化
      ┌────────────────────┼────────────────────┐
      ▼                    ▼                    ▼
   内容裁剪            参数覆盖            品牌与文案
（订哪些）           （怎么算）           （长什么样）
```

### 3.2 定制点清单（三类，可枚举）

| 类 | 定制点 | 存储位置 | 举例 |
|---|---|---|---|
| **① 内容裁剪** | 订阅哪些模块 / 哪些卡片 | `client_rules.modules` / `card_patterns` | 只收「短线精灵 + 快照 + 复盘卡」 |
| | 永久排除项 | `client_rules.exclude_patterns` | 排除机构卡 `gangtise_*` |
| | 推送时段 | `client_overrides['push.window']` | 只在 09:25–15:00 推 |
| **② 参数覆盖** | 情绪/晋级阈值 | `client_overrides['threshold.*']` | 晋级率阀门客户自定 |
| | 标的池 | `client_overrides['pool.watchlist']` | 客户自己的自选池 |
| | 板块白名单 | `client_overrides['sector.allow']` | 只看通信/半导体 |
| **③ 品牌与文案** | 系统名称 / logo | `client_overrides['brand.*']` | 客户自己的品牌 |
| | 免责声明 / 页脚 | `client_overrides['legal.*']` | 客户法务口径 |
| | 主题色 | `client_overrides['theme.*']` | 覆盖 Token（保持涨红跌绿铁律） |

**共同载体**：一张 `client_overrides(client_id, key, value jsonb)`，键空间用点号前缀分组。
**取值优先级**：`客户覆盖 → 系统默认`，仅两级，不做多级继承（避免配置地狱）。

### 3.3 三条禁止事项

1. ❌ **禁止为客户改代码分支**（`if client == 'xxx'` 一律不允许）。
2. ❌ **禁止为单个客户加特性开关**（新功能要么进基线、要么走配置点；不做一次性开关）。
3. ❌ **禁止同一功能两套实现**（产品版与定制版共用同一组件/接口，只参数不同）。

**一句话原则**：**定制 = 配置的排列组合，不是代码的分叉。**

> 这条原则直接继承你现有系统的成功经验——`shared_rules.md` 作为单一权威、`ENABLE_*` 可逆开关、`client_mirror` 关键词白名单，全都是"配置驱动"的范式。

## 4. UI 技术选型（放开 UI 库后的重评估）

### 4.1 四库对比

| 库 | 主题定制 | 大表格性能 | 中文生态 | 你的熟悉度 | 综合 |
|---|---|---|---|---|---|
| **Element Plus** | 强（CSS 变量，可整体覆写） | **强**（`el-table-v2` 虚拟滚动） | 最好 | **高**（公司项目在用） | ⭐ **推荐** |
| Ant Design Vue | 强（CSS-in-JS token） | 强 | 好 | 中 | 备选 |
| Naive UI | 最强（TS 变量注入 + 全量主题） | 中 | 好 | 低 | 主题最灵活 |
| Arco Design Vue | 中 | 强 | 中 | 低 | — |

### 4.2 推荐：**全站采用 Element Plus**

**理由（按权重排序）**：

1. **复用你已有的组件经验** —— 你的公司后台项目技术栈正是 `Vue 3 + Vite + Pinia + Element Plus`，选它等于把已有熟练度直接迁移到产品上，学习成本为零。
2. **`el-table-v2` 可扛行情表格** —— 虚拟滚动，全市场 5,000+ 行、秒级刷新可用。这解除了 v1 的"性能顾虑"。
3. **CSS 变量主题机制可直接映射现有 Token** —— 你在 `:root` 已有 `--up / --down / --rec / --lead / --warn` 语义色板，Element 的 token 可整体覆写为同一套值。
4. **中文文档与社区最完善**，长期维护风险最低。

### 4.3 落法：三条强制注意事项

| # | 事项 | 原因 | 做法 |
|---|---|---|---|
| **1** | **主题必须走 CSS 变量覆写** | 逐组件 `!important` 会随升级全面崩坏 | 建立 `packages/tokens`，把 Element 变量映射到项目语义 Token；**一处改、全站生效** |
| **2** | **行情大表必须用 `el-table-v2`** | `el-table` 在 1,000 行 + 秒级刷新时明显卡顿 | 行情类表格统一 `el-table-v2`；管理类表格可用普通 `el-table` |
| **3** | ⚠️ **涨红跌绿的语义重映射（最容易出错）** | Element 默认 `success=绿 / danger=红`，与 A 股「涨红跌绿」**完全相反** | 重定义语义变量：`--el-color-danger → 红(涨)`、`--el-color-success → 绿(跌)`；**业务代码禁止直接使用 `type="success|danger"`**，必须走项目语义组件 |

> 第 3 条是**本方案最高优先级的 UI 风险**。你的系统对语义色有明确铁律（改善红 / 恶化绿 / 止损禁打板警示红 / 涨停整行红），一旦被 Element 默认色板污染，会出现"利好显示为绿色"的严重误导。建议封装 `<UpDown>` `<SemanticTag>` 等语义组件，从组件层封死误用路径。

### 4.4 组件映射（哪些用库、哪些自研）

| 区域 | 采用 | 说明 |
|---|---|---|

### 5.1 技术栈定稿

| 层 | 选型 | 说明 |
|---|---|---|
| Web 框架 | **FastAPI + Uvicorn** | 领域计算全在 Python，同语言免胶水 |

| ORM / 迁移 | SQLAlchemy 2.x（异步）+ Alembic | — |

### 5.2 数据库 Schema 草案

```
── 契约层 ────────────────────────────────────────────────
market_snapshots(id, trade_date, rule_version, payload jsonb, created_at)
   UNIQUE(trade_date, rule_version)          ← 同一交易日可有多个规则版本（可回溯）

── 原始层（只增不改，对应 quant-review 的 raw）─────────────
raw_pools   (id, trade_date, kind, payload jsonb, source, fetched_at)   kind: zt|dt|zb|qsgc
raw_index   (id, trade_date, code, kline jsonb, snapshot jsonb)
raw_themes  (code6, themes text[], updated_at)
raw_news    (id, ts, source, title, payload jsonb)                       ← 快讯/龙虎榜/研报

── 领域产物层（对应 features / marketData）───────────────
domain_outputs(id, trade_date, module, key, payload jsonb)
   ← 每个领域模块的 patch 落库；支撑 PARTIAL 重算与审计追溯

── 客户域（见 §1.2）────────────────────────────────────
clients / client_channels / client_rules / push_logs

── 治理域 ──────────────────────────────────────────────
task_runs       (id, task_name, trade_date, started_at, finished_at, status, detail jsonb)
audit_logs      (id, ts, actor, action, target, result, detail jsonb)
backtest_reports(id, trade_date, payload jsonb)
learning_state  (id, key, value jsonb, updated_at)      ← 替代 learning_config.json
```

**三个设计决策**：
- `market_snapshots.payload` 用 JSONB 而非宽表：契约演进不触发 DDL，且与现有 `marketData` 结构天然对应。
- `domain_outputs` 按"模块 + key"落库：这是 quant-review 的 `requires/provides` DAG 的持久化，使 **PARTIAL 重算**（只重跑某模块 + 依赖链）成为一等能力。
- 所有业务表带 `trade_date`：时序查询是主查询模式，直接建索引即可。

## 8. P0 拆解方案（基于实测的两个巨型文件结构）

> 本节是对 `intraday_pulse.py`（2,044 行）与 `live_signal.py`（2,396 行）做 AST 结构分析后的**可执行拆解方案**。
> 结论先行：**两者都无需重写逻辑，只需物理切分**——它们内部的分层已经天然存在。

### 8.1 `intraday_pulse.py`（2,044 行）→ 五层切分

| 现有区块（实测） | 规模 | 归入 | 说明 |
|---|---|---|---|
| 常量区（webhook / 选股宝+东财 URL / `CACHE_DIR` / `PLATE_FOCUS` / `FOCUS_SECTORS` / `SECTOR_CHAIN`） | ~100 行 | **配置层** | 硬编码配置，外置候选 |
| `Fetcher` 类(89) + `_fetch_em_rising` + `_fetch_tx_selfchanged` + `fetch_market` | ~170 行 | **M1 采集网关** | 出网职责 |
| `parse_*` × 15（stocks / plates / newsflash / index / em_market / tx_index / tx_selfchanged / pool / ladder / tomorrow / theme_stocks …） | ~350 行 | **M1 解析** | 纯解析、无状态 |
| `http_get` / `http_post` / `rc` / `query_pct` | ~30 行 | M1 | 接口辅助 |
| `build_sectors` / `build_early_signals` / `build_leaders` / `build_hot_spots` / `build_weak_sectors` / `build_sector_risk` / `build_sector_flow_snapshot` | ~400 行 | **M2/M3/M4 领域** | 计算 |
| `detect_new_events` / `diagnose_dragon` / `seal_quality` / `scan_risks` / `scan_positives` / `compute_sentiment` / `detect_ebb` + `_ebb_*`×4 | ~350 行 | **M2 情绪引擎** | 信号与情绪 |
| `generate_insight` / `build_insight_block` / `_sector_status` | ~95 行 | M3 领域 | 题材逻辑 |
| `md`/`div`/`hr`/`note`/`col` + `build_summary_json` + `build_ebb_card` **+ 两个退役函数** | ~250 行 | **M6 渲染推送** | 卡片 |
| `in_trading` / `today_c` / `now` / `ts` | ~20 行 | 公共 | 与 `common/market_time.py` 去重 |
| `run_mode`(170) + `main`(25) | ~195 行 | **编排层** | 保留 |

**顺带发现（可立即执行的低风险清理）**：`build_top5_card` 与 `build_post_card` 两个函数自带注释「🔒 已退役·仅 debug 工具」，合计约 155 行 —— **先删死代码，再拆结构**。

### 8.2 `live_signal.py`（2,396 行）→ `main()` 是首要目标

| 现状（实测） | 规模 | 判断 |
|---|---|---|
| 开关常量区 | **~40 个 `ENABLE_*` / 阈值常量** | `ENABLE_SECTOR_BOOST_CARD` / `ENABLE_GRADUAL_BOOST` / `ENABLE_SECTOR_FAMILY` / `ENABLE_SECTOR_FLOW_LINE` / `ENABLE_CLIMAX_WARN` / `ENABLE_EBB_ALERT` / `ENABLE_INSTITUTION_L2` / `HIGH_FREQ_INTRADAY` / `REFLOW_PHASE_WIDEN` … |
| 已标注的纯函数 | `_pool_flow`(51) / `_decide_sector_stage`(20) / `_climax_hit`(10) | 注释明确写「**纯函数·供单测锁定**」→ 范式**已在用**，只需系统化 |
| 卡片构建器 | `build_*_card` × 14（资金切换 / 首板 / N字二波 / 回流 / 板块加强 / 核按钮 / 退潮 / 机构 / 板块过热 …） | 可整组归 M6，逐个独立 |
| **`main()`** | **L1438–2391，共 954 行** | ⚠️ **本系统最大的单点复杂度** |

**两条重要结论**：

1. **`main()` 954 行是首要拆解目标**。按「信号源」切分为独立检测器：
   `detect_fund_switch` / `detect_first_zt` / `detect_n_shape` / `detect_reflow` / `detect_sector_boost` / `detect_climax` / `detect_nuke` / `detect_ebb` / `detect_institution`。
   每个检测器**输入 = 快照，输出 = 信号列表**；编排层退化为「收集 → 去重 → 排序 → 推送」。这与 quant-review 的模块 `compute(ctx) -> patch` 完全同构。

2. **~40 个 `ENABLE_*` 开关是产品化的现成资产**。
   它们天然就是 §3.2「内容裁剪」与「参数覆盖」的**定制点载体** —— 产品化无需新设计，**只需外置到配置层并按客户覆盖**。这是本次整合里成本最低、收益最直接的一步。

### 8.3 拆解顺序与风险

| 步 | 动作 | 风险 | 验证方式 |
|---|---|---|---|
| 1 | 删死代码（`build_top5_card` / `build_post_card`） | 极低 | 回归测试 |
| 2 | 常量与 `ENABLE_*` 开关外置到配置层 | 低 | 取值一致性比对 |
| 3 | `intraday_pulse.py` 五层物理切分 | 低 | 各层单测 + 端到端产物**逐字节比对** |
| 4 | `live_signal.py` 的 `main()` 按检测器切分 | **中（最高）** | **影子模式**：新检测器与旧 `main()` 并行跑，输出比对一致后再切 |
| 5 | 收敛「涨停判定」为单一函数 | 中 | 全量历史数据比对 |

**第 4 步建议采用影子模式而非一次性替换** —— 与系统已有的 `relay_shadow.py`（P2-13 影子模式·零侵入）实践一致，可复用同一套对照机制。
