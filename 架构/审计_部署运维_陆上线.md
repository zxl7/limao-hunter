## 1. 部署架构审计

### 1.1 dev / prod 双执行者是否共用 read-route 逻辑？

| 执行者 | 读实现来源 | 路由定义来源 |
|---|---|---|
| 开发期 vite 中间件 (`vite.config.ts:35-87`) | `scripts/lib/read-route.mjs`（单一真源） | `src/shared/api/routes.ts` |
| 命令行体检 `check-data-routes.mjs` | `scripts/lib/read-route.mjs`（同一份） | routes.ts |
| **生产 serve.py** | **Python 重新实现 `read_route`（serve.py:93-159）** | **Python 字典 `PUBLIC_ROUTES`（serve.py:245-368）** |

- ✅ dev 中间件与 CLI 体检**确实共用** `read-route.mjs`（注释见 read-route.mjs:1-12，明确"单一真源"）。
- ⚠️ **prod serve.py 并未 import read-route.mjs**，而是平行移植了一份 Python 实现。两份实现当前语义对齐（单文件 / 目录+pattern / 两层目录 / jsonl 跳半行 / text 原样返回均一致），但**属于双份维护，存在漂移风险**。
- ⚠️ **路由定义也双份维护**（routes.ts vs PUBLIC_ROUTES）。实测对比：routes.ts 83 条、serve.py 82 条；**仅在 dev 有、prod 缺 1 条：`/api/board/leader-daily`**（serve.py 未登记 → 生产环境该路由 404）。其余 82 条两者一致（决策/AI/账户三族两边都有，dev/prod 路由可用性一致，"前端无需区分环境"成立）。

### 1.2 serve.py 健壮性

- **进程模型**：`ThreadingHTTPServer`（serve.py:712）+ 单进程。并发 OK（每请求一线程），但**单进程、无多 worker**；对只读静态/小 JSON 足够。
- **自愈**：launchd `KeepAlive=true`（`com.limao.terminal-serve.plist`）→ 崩溃自动拉起。**但 serve.py 只处理 `KeyboardInterrupt`（serve.py:714-717），无 SIGTERM 处理器**——launchd 卸载/重载发 SIGTERM 时是硬杀，无优雅停机（对只读服务影响小，但长连接/在途请求会断）。
- **超时**：无单请求超时；一个慢读（如读超大 jsonl）只会阻塞该线程，不拖垮整体，但无全局保护。
- **安全默认**：非 loopback 监听且未设 `SHARE_TOKEN` 时**直接拒启动**（serve.py:702-707），优于旧版仅告警。
- ⚠️ **prod `/api/health` 弱于 dev**：dev 版 `healthPayload`（read-route.mjs:165-218）含 `asof`（业务日期）、`kind`、`cadence`；prod 版 `health_payload`（serve.py:195-239）**只有 exists/mtime/age_sec/size，无 `asof`、无 `kind`、无 `cadence`**。因此 prod 健康端点**无法发现"文件在、mtime 新、但内容日期是昨天"这类安静错误**（见 §3.2）。
- ⚠️ **dir 取"最新"口径不一致**：serve.py 按 `sorted(names)[-1]`（**文件名**字典序，serve.py:116）取最新；read-route.mjs 按 **mtime** 取最新（read-route.mjs:176-189）。当文件名非单调（历史日期命名）时，prod 健康探针可能选到旧文件。

### 1.3 迁移到服务器

- ✅ "`LIMAO_DATA_ROOT` 覆写数据根"成立：serve.py:48（`DATA_ROOT = env LIMAO_DATA_ROOT or PROJECT_ROOT`），vite:17（`resolveDataRoot`）。前端构建 `dist` 静态，无需改码。
- ⚠️ **注意**：serve.py 路由同时读 `cache/...` 与 `wealth_code/cache/...`（如 `/api/decision/*`、`/api/ai/*`、`/api/account/*`）。迁移时**两者都要同步**（见 §1.4 缺陷）。

### 1.4 DEPLOY.md 路径 B 的 rsync 真实缺陷（部署正确性 Bug）

DEPLOY.md:88-95 的路径 B 同步命令：
```
rsync -az --delete --exclude='zt_genes' --exclude='decision_log' \
  --exclude='ai_view_*' --exclude='.workbuddy' --exclude='settings.json' \
  cache/*.json cache/**/*.json 用户@服务器:/opt/limao/cache/
```
- ❌ **不同步 `wealth_code/cache/`**：而 serve.py 放开后的 `/api/decision/*`、`/api/ai/*`、`/api/account/*`（2026-10-26 放开，serve.py:316-340）全部读取 `wealth_code/cache/*`。照此 rsync，服务器上这些路由**全部 404 / 无数据**。
- ❌ **排除项过时**：`--exclude='ai_view_*'`、`--exclude='decision_log'` 与已放开路由冲突（`/api/ai/view` 需 `ai_view_*.json`；`/api/decision/archive` 需 `decision_log/`）。
- 建议：rsync 增加 `wealth_code/cache/` → `/opt/limao/wealth_code/cache/`，并删除对 `ai_view_*`、`decision_log` 的 exclude（或改为服务端用 `SHARE_PRIVATE=0` 回退时再排除）。

## 2. launchd 调度健康

### 2.1 真实调度拓扑（纠正"14 launchd 任务"）

| 层 | 实际机制 | 证据 |
|---|---|---|
| 对外 Web + 隧道 + 防睡 | **launchd** 3 个 agent：`terminal-serve`、`terminal-tunnel`、`terminal-awake` | `~/Library/LaunchAgents/com.limao.*.plist`；均 `RunAtLoad+KeepAlive` |
| 盘中脉冲守护（30s/60s 心跳） | **launchd** `pulse-fetcher`（`StartInterval=30`，内部按时段节流 30s/5min/60s/10min） | `com.limao.pulse-fetcher.plist`；`scripts/pulse_fetcher.sh:34-50` |
| 财富密码·竞价验证 | **launchd** `wealth-verify`（`StartCalendarInterval 09:25`） | `com.limao.wealth-verify.plist` |

### 2.3 历史事故与现网缓解

- 用户记忆 **2026-08-13 全天 0 推送、8-14 恢复**：现网已有三重缓解——① `pulse_fetcher.sh` 单实例锁 + 陈旧锁自清（脚本注释 2026-09-15 双实例事故根治）；② `schedule_sentinel.py`（P1-⑥）：交易时段内 ACTIVE 盘中任务 >45min 未成功 → 自动 `pulse_fetcher --force` 补跑 + 推"⚠️调度异常"蓝卡；③ `system_health.py` 全量体检。

## 3. 数据新鲜度与完整性

### 3.1 现网证据（健康）

- 今日写入：`find cache -newermt "2026-10-30 00:00"` = 98 个文件；点名三项 mtime：`intraday_timeline_state_20261030.json 09:50:16`、`theme_rotation.json 09:49:28`、`feedback_matrix.json 09:49:21`（均 2026-10-30）。
- `fetch.log` 末行：`[09:50:17] >>> realtime_push` → 盘中链路**今日活跃**。
- 最旧文件均为 `cache/backups/cleanup_20260911/*`、`cache/decision_log/2026-08-*` 等**历史归档**（按设计保留），非损坏。全仓 5241 文件中 2861 个 >7 天未改 = 历史日频归档堆积，**正常但需注意磁盘增长**。

### 3.2 `/api/health` 能否发现"数据在但口径变了"？

- **prod `/api/health`（serve.py:195-239）不能**：只校验文件存在 + mtime + size，无业务日期 `asof`。示例：若某路由今天没刷新但昨天文件还在（mtime 新），它判"健康"。
- **dev 版能**（read-route.mjs:199, 224-238 `asofOf` 读内容里 `date/asof/ts`）。
- **CLI 版 `system_health.py` 能**：`check_cache_freshness`（169-228）对 `post_close` 类文件比对 JSON `date` 字段与最近交易日（`_json_date` 160-166），可捕获"日期错/连续停摆"；对 `intraday` 类在交易时段内若 mtime<今日 09:25 判 stale。
- **结论**：安静错误（口径/日期变）的防线在 **CLI 体检**，**不在**始终在线的 `/api/health`。建议把 `asof`/`kind`/`cadence` 补回 serve.py `health_payload`，让 dashboard 健康组件与生产端点一致。

### 3.3 半写文件

- `parse_jsonl`（serve.py:78-90 / read-route.mjs:43-57）逐行 try/except 跳过半行 → **写入中文件不会让整批失败**， resilient。JSON 单文件损坏则在 read_route 捕获后返回 `data_unavailable`（serve.py:628-642），不崩服务。

## 5. 监控 / 回滚 / 密钥

### 5.1 监控现状

- ✅ **已有但为手动**：`system_health.py`（`check_automations`/`check_launchd`/`check_cache_freshness`/`check_run_health`/`check_quality_gate`，行 105-346）是全量体检，能发现"任务超期/launchd 未加载/数据陈旧/日期错"。**但它不在 tasks.yaml 28 任务里 → 未被自动定时执行**，只是手动 CLI。
- ✅ **已有自动告警**：`schedule_sentinel.py`（STALE_MIN=45）交易时段自动检测盘中任务超期 → 补跑 + 推蓝卡；飞书各推送卡本身即"数据在产"的风向标。
- ⚠️ **缺口**：① `system_health.py` 未自动跑（建议加 launchd/WorkBuddy 每 30min 交易时段定时 + 有 issues 才飞书告警）；② **无 serve.py 外部存活探针**（见 §2.3）；③ 监控集中在"数据生产侧"，**服务侧（serve.py 进程 / 隧道域名变更）缺持续探活**。

### 5.2 回滚预案（缺失 + 建议）

- ❌ **DEPLOY.md 无回滚章节**（全文 129 行，仅"架构原则/路径A+/A/B/环境变量/验收/进阶"）。现网回滚是隐式的：git revert + 重 rsync，**无书面步骤、无验证点**。
- 建议补一份回滚清单（可纳入 DEPLOY.md）：
  1. **代码/配置回滚**：`git revert <commit>` 或 `git checkout <tag>`；`SHARE_PRIVATE=0` 可秒级把 ai/decision/account 三族恢复 404（serve.py:59,617），无需改码即"逻辑回滚"。
  2. **服务回滚**：`launchctl unload ~/Library/LaunchAgents/com.limao.terminal-serve.plist` → 旧版 serve.py → `load`。
  3. **数据回滚**：`cache/backups/` 已有 `nav_/ai_decisions_/learning_rollback_` 前缀白名单备份（serve.py:365）；新盲区功能上线须先加对应备份点 + 开关。
  4. **验证**：`curl -s --noproxy '*' http://localhost:8000/api/health | jq` 比对 issues 为空；抽样 `curl /api/market/feedback?t=x` 有数据、`/api/ai/view?t=x` 按 SHARE_PRIVATE 预期。
- 原则（与系统一致）：**数据库/数据变更先于代码发布解耦、先兼容后清理**——本系统数据为追加落盘、无破坏性 schema 变更，回滚主要是"停写新格式 + 旧路由仍可读旧文件"，风险低。

### 5.3 密钥管理
