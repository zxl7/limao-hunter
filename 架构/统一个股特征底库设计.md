# 统一个股特征底库（stock registry）· 设计说明

> 立项：2026-10-14 · 用户需求「在系统底层沉淀一个数据源，记录每个个股的特性」
> 权威源：规则以 `config/shared_rules.md`【统一个股特征底库】为准 · 实现以 `common/stock_registry.py` 模块头为准
> 本文件说明**设计取舍与理由**，不重复规则条文。

---

## 一、要解决的问题

此前「个股」在系统里没有统一身份，散落在四处、口径各不相同：

| 位置 | 形态 | 为什么不够 |
|---|---|---|
| `cache/pulse_snapshots/latest.json` | 一次性快照 | 下一轮刷新即覆盖，不累积 |
| `cache/yesterday_zt.json` | 「最近一次」涨停池 | 只代表一个时点 |
| `cache/zt_history/zt_*.json` | 逐日文件 | 跨日查「这只票的题材是什么」要自己拼 |
| `cache/zt_genes/*` | 涨停股性派生指标 | 只有涨停股性，不是通用特征底座 |

底库要提供的是：**一票一个对象，跨日累积，可扩展，且能被实时增量更新。**

---

## 二、入库门槛：与今日表现无关

用户原话：「只要进入系统就沉淀，记录底层数据，和数据的今日表现无关。」

这一条决定了三件事：

1. 盘中抓到的**所有**异动/涨幅榜个股都沉淀，不是只存涨停股；
2. 「今日是否涨停」只是对象上的**一个属性**，不是筛选条件；
3. 未命中的个股**保留原值**——底库不做全量重写，只做增量。

---

## 三、存储方式：SQLite 真源 + JSON 投影

| 维度 | SQLite（**选用**） | 单一大 JSON 读改写 |
|---|---|---|
| 唯一标识 | `PRIMARY KEY(code)` 数据库硬保证 | 手写去重，容易回归 |
| 并发丢更新 | WAL + `BEGIN IMMEDIATE` 事务内读改写 | `common/json_io.save_json` 只防半写，**不防并发丢更新** |
| 字段级合并 | 读改写同事务，天然「有值才写」 | 每次全量 read-modify-write，O(N) |
| 扩展字段 | `ALTER TABLE` / `ext_json` | 靠约定，无 schema |
| 检索 | name / tag / date 走索引 | 全量遍历 |

**代价与对冲**：SQLite 人类不可读，而 `serve.py` 只认 JSON 文件。
→ 导出只读投影 `cache/stock_registry/stock_registry.json`，**前端读取方式零改动**。
→ 选股宝快照在 `latest.json` 落盘后按代码增量合并：`hot_spots`、`top5`、`leaders`、`early` 提供题材，`top5.official.boards` 提供行业板块；无代码只给名称的记录不猜、不建对象。
→ **投影同步契约（2026-10-15 用户定）**：盘中每 30 秒写 SQLite，但不刷投影；盘后 `ingest_eod_snapshot()` 成功完成后刷新一次。这样盘中读投影最多滞后到盘后，避免高频全量序列化；刷新失败只记日志，不影响盘后归档主链。需要手工重导时运行 `python3 scripts/stock_registry.py refresh`。测试期未显式传 `out_path` 会由 `_projection_write_blocked` 拦截，防止临时库覆盖生产投影。

`cache/` 已在 `.gitignore`，DB 与投影都不入库。

## 四、数据结构

### 4.1 六张表

| 表 | 职责 | 关键约束 |
|---|---|---|
| `stocks` | 主表，一票一行：长期属性 + **当日快照** + 元数据 | `code` 主键 |
| `stock_daily` | 逐日观测，append-only | PK `(code, trade_date)` |
| `stock_tags` | 多值标签，**题材与行业分列** | PK `(code, tag_type, tag_value)` |
| `stock_observations` | 原始观测审计，可回放 | `dedup_hash` 唯一 |
| `stock_name_alias` | 名称→代码别名 | PK `(name, code)`，**名称只做检索** |
| `stock_pending_review` | 无代码 / 名称歧义 / 脏数据 | 待人工确认 |

### 4.2 字段分三类（混用会出事）

- **长期属性**：`code / symbol / name / market / is_20cm / industry / first_seen_date`
- **逐日属性**：`limit_up_now / limit_up_touched / limit_up_close / boards / pct / price / seal_yi / hs`
  —— 必须与 `daily_asof_date` **同读**
- **元数据**：`source / last_seen_ts / last_updated_ts / update_count / data_quality`

为什么长期与逐日必须分开？因为**同一列里既有"今天"又有"永远"**，读的人一定会把
`pct`（某天的涨幅）当成"当前涨幅"。分开后，逐日字段自带日期语义，旧值不会被误读。

### 4.3 「今日是否涨停」为什么是三个字段

**因为数据源看不到全市场。** `limit_up_stocks` 数量自洽 ≠ 全市场完整；
「不在涨停名单里」**绝不等价于**「今天没涨停」。把三态压成一个布尔，必然要么造假、要么丢信息。

| 字段 | 语义 | 变化规则 |
|---|---|---|
| `limit_up_now` | 当前是否封板 | 同日按 `asof_ts` 新者胜；1→0 = **已开板**（显式变更，必须接受） |
| `limit_up_touched` | 当日是否曾触板 | **闩锁**：一旦为 1，当日永不回 0 |
| `limit_up_close` | 是否收盘涨停 | **仅盘后权威源可写**（禁用涨幅阈值冒充收盘） |

三者都允许 `NULL` = 未知。取用统一走 `is_limit_up_today()`，返回 `(值, basis)`：

```
close → now → touched → unknown
```

`basis` 说明结论来源，避免把盘中态当收盘态用。另外投影与对象都带
`daily_is_latest_trading_day`：为 `False` 表示**这条数据属于更早的交易日**
（该票之后没再进入系统）——⛔ 这种情况不得读成"今日涨停"。

### 4.4 证据强度分级

不同来源的 `up` 字段可信度不同，**不可混为一谈**：

| 来源 | 字段含义 | 允许写什么 |
|---|---|---|
| 选股宝异动池 `up_limit` | 当前封板 | `limit_up_now` / `limit_up_touched` |
| 东财涨幅榜 `rising[].up` | **涨幅阈值推断**（19.9/9.9），不是确切涨停 | 仅在为真时作弱证据写 now/touched |
| 必盈涨停池 `zt_list` | 全市场涨停名单（盘后） | `limit_up_close`（唯一权威） |

即便 `up` 为假也**不写 0**。

## 五、更新与合并规则

1. **命中即 upsert，未命中不动**：只写实际观测到的票，不做全市场扫描。
2. **有值才写**：入参 `None` ⇒ 该列不动。缺失**绝不覆盖**已有非空值。
3. **跨日整体轮换**：`trade_date` 前进时，当日快照整体换新（未提供的置空）。
   旧值不丢——它们留在 `stock_daily` 里。这样"昨天封板"不会残留成"今天封板"。
4. **同日合并**：按 `asof_ts` 新者胜；同值写入**不增加** `update_count`。
5. **乱序保护**：旧 `asof_ts` 晚到时，不覆盖当前态；但闩锁 `max`、标签、别名照常累计。
6. **代码规范化**：`600000.SH` / `sh600000` / `" 600000 "` → 主键 `600000`，原值存 `symbol`。
   用前后向断言卡死**恰好 6 位**——`6000000` 不得被截成 `600000`（否则凭空造出代码）。
7. **名称歧义不猜**：同名多代码且无从辨别 → 进 `pending_review`，不建重复对象。
   名称**只用于检索与别名累积**，绝不作为主对象键。

### 幂等与去重

- `stock_observations.dedup_hash = sha1(code|trade_date|source|规范化字段串)` + 唯一索引
  → 同日同源同值的重复观测只留一条。
- `symbol` 采用**首次登记为准**：多源写法（`600000` vs `600000.SH`）交替出现时，
  不会把 `update_count` 刷成噪声。

## 六、异常与缺失处理

| 场景 | 策略 |
|---|---|
| 接口失败 / 字段缺失 | 留 `NULL`，不编、不猜、**不把"缺席"写成"未涨停"** |
| 脏类型 `"false" / "None" / NaN / ""` | 严格解析器 → 三态；非法值记 `dirty_type:<字段>` |
| 非交易日 / 未来日期 / asof 不可解析 | **拒绝写入**（回填需显式 `allow_backfill=True`） |
| 并发锁超时 | **大声失败**，绝不静默丢弃 |
| 测试期未注入路径 | **当场 `RuntimeError`**（复刻 `zt_archive._guard_test_write` 血案防线） |
| 底库自身异常 | 两处 hook 全 `try/except`：**不得中断盘中/盘后主链** |

### 关于 `bool("false") is True`

旧代码 `up = bool(it[7])` 对字符串 `"false"` 会判真——这是**真实事故源**。
底库的解析器只认白名单（`1/true/yes/是` ↔ `0/false/no/否`），
其余一律 `None` + 脏标记，**绝不把任意非空字符串当 True**。

## 七、入口覆盖

### 一期（真正接入并验证，仅 2 处）

| 入口 | 位置 | 写入 |
|---|---|---|
| 盘中 | `scripts/intraday_pulse.py::run_mode()`（latest.json 落盘后、`dry_run` 返回前） | `now` / `touched` + 题材 `plates` |
| 盘后 | `scripts/zt_archive.py::write_archives()`（**双目录循环之外**，仅一次） | `close` + 行业 |

盘后 hook 放循环外的原因：循环按目录数执行，放里面会**重复记账**。
且该单点同时覆盖 `record_zt_snapshot` / `capture_daily` / `ensure_today_archive`
三条调用者，⛔ **不新增涨停归档写入路径**。

### 二期：全量命中队列 + 技术派生（2026-10-15 已接入）

一期解决「所有路过股票进入事实底库」；二期把当天命中的**全部代码**自动进入技术计算队列：

| 节点 | 触发 | 写入 | 口径 |
|---|---|---|---|
| 盘中每轮 | `ingest_intraday` / `ingest_xgb_snapshot` 成功 | `stock_technical_queue` | 命中即入队，队列幂等；不要求涨停 |
| 盘后归档后 | `capture_daily.py` 末段 `_process_stock_technical()` | `stock_technical_daily` | 对当天 `stock_daily` 的全部代码计算，失败不阻断主链 |
| 手动补算 | `python3 scripts/stock_registry.py technical --date YYYY-MM-DD` | 同上 | 可重跑，便于回填/验证 |

技术派生使用统一腾讯前复权日K，按日保存、可重算，不回写 `stocks.industry` 或 `stock_tags`：
`MA5/10/20`、近 `3/5/10` 日收益、前一窗口 `20/60/120` 日高点、阶段新高标记、均线多头、5日量比、数据完整性。

**全量与深挖分离**：事实层「被系统看见就写」；技术层「当天所有命中都算」；AI研究层以后只对重复出现/进入候选/用户主动提问等对象生成候选观点，不能把观点升级成事实标签。

> 二期仍不写买卖结论；技术数据缺失记 `stock_technical_queue.status=error` 和原因，不填零、不用邻近日期冒充。

### 三期：核心读取源灰度接入（2026-10-15 已接入首批）

二期以前解决“所有路过股票都沉淀、盘后统一算技术”；三期开始解决“业务个股事实不再各自读取旧文件”。

统一只读适配层：`wealth_code/adapters/stock_registry_reader.py`。

| 消费入口 | 默认行为 | 旧数据边界 | 回滚 |
|---|---|---|---|
| `wealth_code/core/defense_gate.py::load_zt_series()` | 生产默认读取 `stock_daily.limit_up_close=1` 的代码/日期/板数 | 缺料时降级 `cache/zt_history`；显式传 `root` 永远走旧 JSON，供测试/回放 | `STOCK_REGISTRY_READ_MODE=legacy` |
| `wealth_code/adapters/input_zt.py` | 底库主读当日涨停事实；旧 `yesterday_zt.json` 补 `fbt/zbc/cje/lt/zsz` 等暂未结构化字段 | 底库无当日收盘事实时回退原选股宝适配 | 同上，或 `WEALTH_USE_STOCK_REGISTRY=0` |
| `wealth_code/pipelines/pipeline_verify.py::_load_full_zt_rows()` | 底库主读完整收盘涨停代码/板数/行情，旧 `cache/zt_history` 只补未结构化字段 | 底库无当日记录时回退旧归档 | `STOCK_REGISTRY_READ_MODE=legacy` |

读取侧铁律：底库主读的是**个股事实**；`latest.json` 仍负责盘中市场快照，`candidates-*.json` 仍是策略产物，`feedback_matrix`/资金/情绪/AI 台账不迁入个股底库。字段缺失不编造，旧文件只做明确的字段补充或降级，不把两套口径静默拼成新的事实。

后续三期扩展顺序：先把底库读取接入展示补齐，再迁移 `leader_cycle`/`reflow_scan` 等历史查询；待 `fbt/zbc/cje/lt/zsz` 等字段进入独立事件/逐日扩展表后，再评估完全替代涨停归档读取。每个消费模块单独灰度、双读对账、可独立回滚。

### 3.2 策略派生：板块联动事实与竞价纪律（2026-10-22）

个股底库解决的是「一票是谁、当天看见了什么、跨日有哪些客观观测」；**候选池的板块联动不是个股长期身份**。它依赖某一交易日的完整涨停池、当期题材映射和次日 09:25 报价，因此只写入候选/验证策略产物，不回写 `stocks` 或 `stock_tags`。

| 层 | 产物 | 写入时点 | 读写边界 |
|---|---|---|---|
| 盘后结构事实 | `linkage_facts_v1` | `pipeline_eod` 在题材映射、完整涨停池归并之后 | 记录 `theme_pool_zt_count`、外部计数、来源冲突、映射指纹与数据质量；不含买卖判断 |
| 盘后预案提示 | `linkage_discipline_v1` | 与事实一起标记候选 | `prefer/neutral/caution` 只反映策略提示，不删票、不改分、不重排 |
| 次日竞价裁决 | `linkage_discipline_v1`（带 `auction_status`） | `signal_eval` 与 `pool_call` 同批 09:25 报价 | 可输出 `block`；仅作为当日候选参与限制，不沉淀成长期标签 |

**为何保留两套题材计数**：`theme_pool_zt_count` 是按冻结题材映射对**完整涨停池**的聚合，是“昨日是否独苗”的主事实；`theme_reported_zt_count` 是外部板块统计，只用于核验。旧实现的 `theme_mates_cnt=max(pool, external)` 保留给旧卡片/策略兼容，但不能被新纪律拿来确认独苗或联动，否则会抹平映射差异、源滞后和统计口径冲突。

**数据质量边界**：旧候选没有完整池计数、题材缺失、映射异常 → `eod_status=unknown`；次日没有同题材成员可核验报价 → `auction_status=unknown`。两种 unknown 都不是负面事实，不能写成“同题材 0 家红开”，也不能触发硬拦。

**默认裁决**：`THEME_LINKAGE_CANDIDATE_MODE=soft` 时，只有「昨日完整池确认独苗 × 当日 1~2 板 × 今早已有同题材有效报价且全未红开」才由 `signal_eval` 和 `pool_call` 同时降为观察。高标独立票默认留给既有龙头/锚点/位置等体系；只有显式 `strict` 才扩大板数范围。`off / annotate / soft / strict` 都可在不修改历史事实的前提下切换或回滚。

**卡面原则**：渲染层只读策略产物并翻译为「同题材有梯队」「今早同题材继续走强」「昨日同题材仅它涨停」「今早同题材数据不足」「同题材没跟上」。不得把 `linkage_facts_v1`、`source_conflict`、计数分歧等内部结构直接推给用户。

```bash
python3 scripts/stock_registry.py init
python3 scripts/stock_registry.py backfill [--since YYYY-MM-DD] [--dry-run]
python3 scripts/stock_registry.py stats
python3 scripts/stock_registry.py get 600000

python3 scripts/stock_registry.py prune [--keep-days 40]

回填**只读本地归档、非网络、幂等可重跑**：
素材 = `cache/zt_history/zt_*.json`（+ 镜像目录补缺日）+ `cache/yesterday_zt.json` + `cache/zt_genes/pool_*.json`。
只对池内个股写 `1`，**绝不为名单外写 `0`**。

重跑：新增 0 | 更新 0 | 无变化 4082      ← 幂等

```

## 十、边界

本层是**客观特征沉淀**，不产出任何买卖结论（对齐 `shared_rules`【数据获取与 AI 决策边界】）。

与 `zt_genes` 的分工：后者是**派生指标**（涨停频率/炸板率/晋级率），本层是**对象底座**，
两者不互相替代——`zt_genes` 可以从本层取数，但本层不依赖它。
