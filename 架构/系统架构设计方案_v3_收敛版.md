> **一句话结论：不要重构。你的系统已经是产品了，缺的是一个 HTTP 端口和三个补丁。**

- 前序：`系统架构设计方案_v1.md`（完整设计）、`系统架构设计方案_v2.md`（拍板落地）
- 本版定位：**推翻 v1/v2 的工作量假设**，保留其技术判断
- 依据：2026-09-14 对本机资产的第二轮实测（三个决定性事实，见 §2）

## 0. 为什么"还是很难"——先诊断

不是架构难，是**范围失控**。v1/v2 把三件彼此独立的事混在一张路线图里平铺开了：

| 混在一起的三件事 | 真实优先级 | v1/v2 的处理 |
|---|---|---|
| ① 让客户能用上 | **最高（现在）** | 排在 P3（第六期） |
| ② 把 44 个脚本拆成 7 模块 | 低（以后） | 排在 P0（第一期，前置） |
| ③ 让它"架构漂亮" | 无（不需要） | 贯穿全文 |

**复杂度预算对比：**

| 指标 | v2 方案 | v3 方案（本版） |
|---|---|---|
| 新增代码量 | 约 15,000 行 | **约 200 行** |
| 新增技术栈 | FastAPI + PG + Redis + Docker + Nginx + Element Plus + Vue3 SPA + Parquet | **0**（Python 标准库） |
| 要动的现有文件 | 44 个脚本 + 3 套前端 | **3 个新文件，现有文件 0 改动** |
| 见到效果 | 3–6 个月 | **1 天** |
| 失败回滚 | 极难 | 删一个文件 |

用户感受的"难"是真实的——那个方案确实重。**重的原因不是系统复杂，是我把一个"加壳"问题按"重写"来答了。**

## 2. 三个决定性实测事实（它们改变了结论）

### 事实 1：`watch.html` 已经是"服务端预渲染 + HTTP 增量刷新"的双模页

`HTML/gen_watch.py` 的 docstring 自述（原文）：

```
架构（与服务端预渲染一致，混合刷新）：
  - 生成时内嵌 latest.json + prev.json + 短线信号 + 候选池快照（file:// 双击即看）
  - 前端 30s fetch '../cache/pulse_snapshots/latest.json' + short_spirit_signals.json 增量刷新（HTTP 下实时）
```

实测 HTML 内确实存在：

```js
fetch('../cache/pulse_snapshots/latest.json',{cache:'no-store'})
fetch('../cache/pulse_snapshots/prev.json',{cache:'no-store'})
fetch('../cache/pulse_snapshots/auction_live.json',{cache:'no-store'})
fetch('../cache/short_spirit_signals.json',{cache:'no-store'})
```

**含义**：这不是一个需要改造的静态页，**它已经是一个读 JSON 的前端应用**。只要有一个 HTTP 服务指向项目根目录，`../cache/...` 自动解析，页面立刻变成实时的、网络可访问的产品。**零代码改动。**

### 事实 2：统一入口已经存在

- `dashboard.html` 实测含 **9 个 Tab**：`tab-rotation` / `tab-intraday` / `tab-mainline` / `tab-return` / `tab-trade` / `tab-flow` / `tab-fundmon` / `tab-record` / `tab-stack`
- `watch.html` 顶栏已有横向链接：`<a class="nav-link" href="dashboard.html">📋 聚合看板</a>`
- 即：**"狸猫系统静态页面 + 另一个看盘页"的融合，已经做完了。**

需求里"融合为统一入口"这件事的剩余工作量，主要是把 `quant-review` 的构建产物拷进同一目录 + 加一个导航项。不是架构工程。

### 事实 3：客户台账已经存在，且已是声明式

`config/settings.json` 实测内容：

```json
"client_mirror": {
  "enabled": true,
  "rules": [{
    "client_key": "feishu_webhook_jiang_kunyang",
    "client_name": "蒋坤阳",
    "card_patterns": ["short_spirit"],
    "title_patterns": ["盘中快照", "复盘"],
    "prod_card_patterns": ["fupan", "review"],
    "exclude_patterns": ["gangtise"]
  }]
}
```

这正是用户第 1 条拍板要的「**纯记录和调用**」形态：一个客户 = 一行声明 = 打标 + 过滤。已四类命中规则、已硬门（测试群不镜像）、已失败不阻断。**台账化已实现约 90%**，缺的只是把这段从 `settings.json` 里抽成独立文件。

### 三条事实的合力

```
v1/v2 假设：                     实测：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
需要重写前端 ────────────→ 不需要，watch.html 已是 fetch-JSON 应用
需要设计统一入口 ────────→ 不需要，dashboard 9 Tab + 双页互链已存在
需要从零搭客户台账 ──────→ 不需要，client_mirror 已是声明式台账
需要服务化 44 个脚本 ────→ 不需要，脚本已写 JSON 到 cache，这已是数据层
```

**结论：缺的不是架构，是三个补丁。**

## 3. 收敛后的整体架构

不新增层级。**现状即架构**，只补中间一个进程：

```
┌─────────────────────────────────────────────────────────────┐
│  采集与计算层（本机·现有 44 脚本·完全不改）                    │
│  pulse_fetcher / intraday_pulse / live_signal / board_core   │
│  common/{http_client,em_flow,...} — 唯一出网口                │
└────────────────────────┬────────────────────────────────────┘
                         │ 写（已存在的行为，不改）
┌────────────────────────▼────────────────────────────────────┐
│  数据层 = cache/ 目录（现有 97MB / 1977 JSON·这就是 API）      │
│  pulse_snapshots/latest.json ← 62KB，已是完整快照响应体        │
│  short_spirit_signals.json / candidates.json / board_core/…   │
└────────────────────────┬────────────────────────────────────┘
                         │ 读
┌────────────────────────▼────────────────────────────────────┐
│  ★ 服务层 = serve.py（唯一新增·约 200 行·含访问白名单）         │
│  · 静态文件（白名单内）  · /api/*（3 个只读接口）              │
│  · 访问日志 → clients.json 台账                               │
└────────────────────────┬────────────────────────────────────┘
                         │ HTTP
┌────────────────────────▼────────────────────────────────────┐
│  展示层（现有·完全不改）                                       │
│  dashboard.html(9Tab) │ watch.html(双模) │ fund_flow_monitor  │
│  + quant-review/dist 拷贝进 static/                           │
└─────────────────────────────────────────────────────────────┘
```

**架构增量 = 一个 `serve.py`。** 其他四个方块全部是"已经存在、不再改动"。

### 为什么不做 FastAPI / PG / Redis（现在）

| 组件 | v2 的理由 | v3 的反驳 |
|---|---|---|
| FastAPI | 统一网关、五组路由、30 个接口 | 现在全部数据需求 = "读一个 JSON 文件返回"。`http.server` + 一个路径映射就是全部。等真的出现"按客户参数动态裁剪"再上框架。 |
| PostgreSQL | JSON 按日落无法支撑多租户并发 | 当前并发的真实量级：**1–3 个客户偶尔打开一个页面**。`http.server` 单线程都够。JSON 文件零迁移成本。 |
| Redis | 热数据缓存 | `latest.json` 62KB，OS 页缓存就是最好的缓存。 |
| Docker | 环境一致性 | 现在只有一台机器。**先本地跑通，迁移时再容器化**（用户第 3 条拍板）。 |
| Vue3 SPA 重写 | 工程规范 | 现有 HTML 已能跑且已验证。**重写的唯一收益是"代码更好看"，成本是全部功能重新回归测试。** |

**共同判据**：每一项的引入都必须回答"它解决了现在就存在的什么痛点"。以上五项目前都答不上来。

## 4. 三个补丁

### 补丁 A：`serve.py`（核心·约 200 行）

**职责**：把 `file://` 变成 `http://`，且**只暴露该暴露的**。

```
serve.py
├─ 静态路由（白名单制）
│    /                      → HTML/dashboard.html
│    /watch                 → HTML/watch.html
│    /flow                  → HTML/fund_flow_monitor.html
│    /quant/*               → static/quant-review/（构建产物）
│    /assets/*              → 前端静态资源
│    /data/latest.json      → cache/pulse_snapshots/latest.json    ★ 显式映射
│    /data/short_spirit.json→ cache/short_spirit_signals.json      ★ 显式映射
│    /data/candidates.json  → cache/pulse_snapshots/candidates.json ★ 显式映射
│
├─ API 路由（只读·3 个）
│    GET /api/health        → 系统状态（守护/新鲜度）
│    GET /api/snapshot      → latest.json 转发 + 统一 meta 包装
│    GET /api/client/{key}  → 按台账返回该客户的内容包与可见数据
│
└─ 访问日志 → 追加 cache/access_log.jsonl（台账化的"调用"记录）
```

**⚠️ 必须实现的安全约束（v1/v2 漏掉的关键风险）**

如果直接 `python3 -m http.server` 在项目根目录启动，会**同时暴露**：

| 暴露内容 | 后果 |
|---|---|
| `config/settings.json` | **飞书 webhook 完整密钥**（含正式群、客户群 hook） |
| `cache/ai_view_*.json` | AI 每日决策与参与判定（自用策略泄露） |
| `cache/zt_genes/`（62MB） | 全部历史涨停基因明细 |
| `cache/decision_log/` | 决策链路全记录 |
| 目录列表 | 整个工程结构可被枚举 |

所以 **`serve.py` 必须是白名单制**：只放行上表列出的路径，其余一律 404。这是"用内置 `http.server` 先跑通"和"写 200 行 serve.py"之间的**唯一实质性差别**，也是必须写的理由。

### 补丁 B：`clients.json` 外置

把 `settings.json` 里的 `client_mirror.rules` 抽为 `config/clients.json`：

```json
{
  "clients": [{
    "key": "feishu_webhook_jiang_kunyang",
    "name": "蒋坤阳",
    "enabled": true,
    "level": "A",
    "channels": {
      "feishu":  { "card_patterns": ["short_spirit"], "title_patterns": ["盘中快照","复盘"],
                   "prod_card_patterns": ["fupan","review"], "exclude_patterns": ["gangtise"] },
      "web":     { "modules": ["snapshot","ladder","flow"] }
    },
    "tags": ["核心客户"]
  }],
  "access_log": { "enabled": true }
}
```

**关键设计**：`channels.feishu` 字段**逐字保留现有四类规则名**，`channels.web` 为新增（现在留空或只填 `["snapshot"]`，接门户时才用）。

**改动量**：`push_card.py` 的 `load_mirror_config()` 换读取源——**一行**。`mirror_targets()` 的匹配逻辑、测试群硬门、自指跳过、`main()` 调用点**全部不动**。已实测确认（`push_card.py` 465 行，改动面仅两处）。

顺带可选补一行：镜像成功后写 `push_logs`（谁在什么时候收到了什么卡）。这是用户说的"**纯记录和调用**"里的"记录"，成本约 10 行。

### 补丁 C：资产并入同一静态目录

| 资产 | 并法 | 成本 |
|---|---|---|
| `quant-review` 构建产物 | `vite build` → dist 拷进 `static/quant-review/`，入口加一个 Tab 或导航链接 | 低 |
| 「股票异动监控.html」（Desktop/顺势而为📈） | 拷进 `HTML/`，改其数据源为 `/data/*` | 低（若原本是自包含 HTML，先原样纳入） |
| 大涨小程序 | **不能并入 Web 入口**——见下 | — |

**⚠️ 必须澄清的技术事实：微信小程序无法融入 Web 统一入口。**

小程序运行在微信客户端沙箱内，**不能作为 Web 页面的子页面 / iframe / 路由**。这是平台机制，不是工程量问题。三个可选处理：

| 选项 | 做法 | 评价 |
|---|---|---|
| a. 保留独立端 | 小程序只把数据源从"直连同花顺"改为"调本系统 API" | **推荐**。最小改动，保留微信生态入口价值 |
| b. H5 重写 | 用 Web 技术重写一份小程序 UI，融入入口 | 成本高，且丧失微信端（小程序码/分享/免下载）优势 |
| c. 仅放入口 | Web 入口放一个"微信扫码使用"区块 | 可作为 a 的补充 |

所以"三资产融合"的准确表述应为：**两 Web 资产同源融合 + 小程序后端点统一**。

## 5. 技术选型的减配表（含升级触发条件）

| 层 | v2 选型 | **v3 现在用什么** | 升级触发条件 → 升级成什么 |
|---|---|---|---|
| 服务 | FastAPI + Uvicorn | **`http.server` + 白名单路由** | 需要「按客户实时参数动态生成」→ FastAPI |
| 存储 | PostgreSQL | **`cache/*.json` 文件** | 需要「跨日复杂查询 / 事务」→ SQLite → PG |
| 台账 | 4 张表 | **`clients.json` 单文件** | 客户 > 30 或需要权限矩阵 → SQLite |
| 缓存 | Redis | **无** | 出现真实读延迟 → 再说 |
| 前端 | Vue3+Vite+TS SPA | **现有 HTML 不动** | 需要「多客户差异化模板」→ Vue3 |
| 管理台 | Element Plus 全站 | **暂不建管理台** | 客户 > 10 或改配置需要非技术人操作 |
| 部署 | Docker Compose | **`python3 serve.py` + launchd** | 迁服务器时 → Docker Compose |
| 交付 | Web URL + Tauri | **公网 HTTP URL** | 客户明确要求桌面图标 → Tauri 壳 |
| 调度 | — | **launchd（现有 24 个任务不动）** | 迁服务器时 → cron/systemd |

**这张表本身就是架构**。它规定了系统在每个规模档位用什么，避免提前引入。

## 7. 演进阶梯（每级都完整可用，可停在任何一级）

| 级别 | 内容 | 客户能看到什么 | 成本 |
|---|---|---|---|
| **L0** | 现状：本机 `file://` 打开 | 只有你自己 | 已完成 |
| **L1** | + `serve.py`（白名单静态服务） | **局域网/公网 URL，实时看盘** | **1 天** |
| **L2** | + `clients.json` + 访问日志 | 台账可见：谁、何时、看了什么 | 半天 |
| **L3** | + 量化站并入 + 异动页并入 + 小程序接 API | 完整三资产入口 | 2–3 天 |
| **L4** | + 拆 `intraday_pulse`/`live_signal`（影子模式） | 无变化（纯内部质量） | 数周 |
| **L5** | + FastAPI/SQLite/管理台（按需单项升） | 差异化内容包 / 自助配置 | 按需 |

**关键**：L1 就已经是"可交付给客户的产品"。L2–L3 是完善。L4–L5 是**有真实反馈之后**才做的事。

原 v2 的 P0（先拆巨型文件）在本阶梯里被降为 L4——因为**在只有 1 个客户、需求最不确定的时候做最重的重构，是全项目风险最高的决策**。

## 8. v2 里哪些结论仍然有效（保留，只是推迟）

| v2 结论 | v3 处置 | 理由 |
|---|---|---|
| **Element 默认色板 `success=绿` 与 A 股涨红跌绿相反** | ✅ **保留为最高优先级 UI 风险** | 一旦引入 Element 必踩。触发时须封 `<SemanticTag>`、禁 `type="success\|danger"` |
| **`watch.html` 双模设计必须保留** | ✅ **保留为硬约束** | 实测已确认它是"file:// 双击可看 + HTTP 实时"的能力来源，是全部资产里最被低估的工程资产 |
| 数据契约（`MarketSnapshot`）思想 | 🔶 **降级为命名约定** | 不建 `packages/contracts`，只在 `serve.py` 的 `/api/snapshot` 里做一层 `meta` 包装与字段校验 |
| `intraday_pulse.py` / `live_signal.py` 拆解方案 | 🔶 **推迟到 L4**，方案存档 | 方案本身有效（`live_signal.main()` 954 行是全系统最大单点），但排期推后 |
| 「产品基线 + 三类定制点」 | 🔶 **推迟**，先只开"内容裁剪"一类 | 现有 `ENABLE_*` 开关约 40 个已是载体，产品化时外置即可 |
| 模块化单体（非微服务） | ✅ **升级为整个 v3 的前提** | v3 走得更远：连"模块化"都暂不做 |
| 大涨 `rules.js` 四档异动口径 | ✅ 保留 | 与具体架构无关 |
| Web 主推 + Tauri 可选 | ✅ 保留 | 与具体架构无关 |

**v3 不推翻 v2 的技术判断，只推翻它的工作量假设和工作顺序。**
