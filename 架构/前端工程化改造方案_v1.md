# 前端工程化改造方案 · v1

> **核心诊断：你其实没有"前端"。**
> 你有一个 **2,637 行的 Python 程序在拼 HTML 字符串**，它的产物叫 `dashboard.html`。
> 所以"前端不够工程化"的准确表述是——**前端还不存在**。这不是重构，是**第一次建立前端**。
>
> 配套：`系统架构设计方案_v3_收敛版.md`（后端结论保留，本文修正其"前端不动"的判断）

## 1. 技术债实证（不是感觉，是量出来的）

| 现象 | 实测证据 |
|---|---|
| 前端逻辑住在 Python 里 | `gen_dashboard.py` **2,637 行**，含 **20 个 `render_*()` 函数**，每个返回 HTML 字符串 |
| 产物不可读 | `dashboard.html` 644 行 / **193KB** —— 单行最长 **51,881 字符**（L456） |
| CSS 无统一入口 | 每个 `<div class="tab-pane">` **内部再嵌一个 `<style>` 块**（如 `#tab-rotation` 内自带 `.rot-tag/.tl-*`） |
| 数据走 HTML 属性 | `RAW = JSON.parse(host.getAttribute('data-items') \|\| '[]')` —— 把 JSON 塞进 DOM 属性再取回 |
| 拼接痕迹外露 | 属性引号用单引号：`<span class='rot-tag'>PCB板</span>`（Python 字符串拼接的指纹） |
| 双份取数逻辑 | Python 侧 `_stock_triple` / `_qt_batch` 拉腾讯盘口；`watch.html` 的 JS 侧又自己算一遍 `buildStats` / `buildFlow` |
| 无类型、无单测、无法 diff | 字符串拼接的产物不具备任何接口约束 |

**"后端可用"这个判断是准确的**，实测支持：

- 前端全部数据只来自 **4 个 JSON**（`latest` / `prev` / `auction_live` / `short_spirit_signals`）
- 加上 dashboard 独用的 `feedback_matrix` / `theme_rotation` / `sector_flow_*` / wealth 数据，合计约 **9 个数据源**
- 调度由 `com.limao.pulse-fetcher` + `com.limao.wealth-verify` 双守护承载，数据每 30s 落盘

→ **这就是一个可用的数据服务**，只缺一个 HTTP 出口。

## 2. 资产分级：什么留、什么换

### 保留（这些是资产，不是债务）

| 资产 | 为什么留 |

| **CSS Token**（`:root` 变量） | `--up:#ee2500` / `--down:#0a8f3c` / `--rec:#8b5cf6` / `--lead:#e8940a` / `--warn:#0d9488` —— A 股语义色已定稿，原样继承 |

### 替换

| 替换对象 | 换法 |
|---|---|
| `gen_dashboard.py` 的 **渲染部分**（20 个 `render_*` + `render()` 组装 + 内嵌 CSS/JS） | → Vue 组件 + 视图 |
| `dashboard.html`（193KB 拼接产物） | → 前端构建产物 |
| 数据塞 HTML 属性（`data-items`） | → typed API client |
| 散落的内嵌 `<style>` | → `styles/tokens.css` + SFC `<style scoped>` |

### 保留但改造

| 对象 | 处置 |
|---|---|
| `gen_dashboard.py` 的**数据准备部分**（`_load_wealth` / `_load_sector_flow_snapshot` / `_load_panqian` / `_load_theme_rotation` / `_stock_triple` / `_qt_batch` / `build_series`） | **保留为后端逻辑**，转为 API 的数据源。这些有真实取值/计算逻辑，不能丢 |

## 5. 数据层设计（前端工程化的最大红利点）

### 现状问题

Python 侧到处 `d.get("sentiment_detail")`、`fb.get("promote_rate")` 裸取，字段名一改就静默出错。前端 JS 侧同理。

### 做法：`src/api/types.ts`

```ts
export interface MarketSnapshot {
  ts: string
  total_zt: number
  sentiment: string
  sentiment_detail: { label: string; score: number; seal_rate: number }
  index: { name: string; pct: number }[]
  limit_down: { count: number; names: string[] }
  broken:     { count: number; names: string[] }
  sector_risk: { declining: Sector[]; inflow_top: Sector[]; outflow_top: Sector[] }
  ladder: LadderItem[]
  leaders: Leader[]        // { name, code, pct, boards, buyable, is_20cm }
  early:   EarlyItem[]     // { sector, type, desc, buy, zt_in_sector }
  hot_spots: unknown[]
  breadth: { up: number; down: number; flat: number }
  ebb: { severity: string; signals: string[]; max_board: number }
  ...
}
```

**做法**：从实际 JSON 反推类型（`/usr/bin/python3 -c` 扫一遍结构），生成首版 `types.ts`，之后由 TS 编译器守卫。

### 需要后端暴露的数据源（9 个）

| # | 前端路径 | 后端文件 | 谁在用 |
|---|---|---|---|
| 1 | `/data/latest.json` | `cache/pulse_snapshots/latest.json` | 几乎所有模块 |
| 2 | `/data/prev.json` | `cache/pulse_snapshots/prev.json` | 对比 |
| 3 | `/data/auction_live.json` | `cache/pulse_snapshots/auction_live.json` | 竞价 |
| 4 | `/data/short_spirit.json` | `cache/short_spirit_signals.json` | 短线精灵 |
| 5 | `/data/feedback.json` | `cache/feedback_matrix.json` | 反馈矩阵（现在前端取不到） |
| 6 | `/data/theme_rotation.json` | theme_rotation 产物 | 轮动/主线/回流 |
| 7 | `/data/sector_flow.json` | `cache/pulse_snapshots/sector_flow_*.json` | 资金监控 |
| 8 | `/data/candidates.json` | `cache/pulse_snapshots/candidates.json` | 候选池 |
| 9 | `/data/wealth.json` | `wealth_code/` 净值+候选 | 交易战绩 |

**关键**：第 5–9 项目前**前端根本取不到**（它们是 Python 内嵌的）。新前端要补齐这些出口——这是"功能填充"的第一步。

## 6. 关键技术决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **Vue 3 + Vite + TypeScript** | 现有 `quant-review` 已验证同栈；你是 6 年前端，这是你的主武器；TS 是本轮最大红利 |
| 2 | **不引 UI 组件库（首期）** | 现有 CSS Token + 手写卡片已定稿，引库立刻撞上"涨红跌绿 vs success=绿"的语义冲突。**定制卡片布局用组件库收益为负** |
| 3 | **数据计算暂时随迁，后置下沉** | `buildStats` / `buildFlow` 等 JS 计算先原样搬进 composable 跑通，稳定后再移到后端。不阻塞进度 |
| 4 | **保留单文件构建** | `vite-plugin-singlefile` → 产物仍是单个 HTML，继承现有 file:// 双击可看的能力 |
| 5 | **dev 期零后端改动** | `vite.config.ts` 的 `server.proxy` 指向 serve.py（或直接用插件把 cache 目录挂进 dev server），前端可独立开发 |
| 6 | **轮询节拍不变** | 30s（继承现有），走 `usePolling` 统一封装，禁止组件内散写 `setInterval` |
| 7 | **ECharts 懒初始化保留** | 现有"切到该 Tab 才 init"的做法正确，抽成 `useEcharts` |
| 8 | **Python 渲染分两步下线** | 先并行（新前端上线但 gen_dashboard 仍在跑）→ 稳定后停 `gen_dashboard` 的渲染调用。**不删数据准备逻辑** |

## 8. 与 v3 的关系

| v3 结论 | 本文修正 |
|---|---|
| 「现有 HTML 能跑就别动」 | ❌ **修正**：`dashboard.html` 不是"能跑的前端"，是"Python 的输出"。**必须重建** |
| 「AI 不需要服务层，静态服务够」 | ✅ 保留：`serve.py` 白名单方案不变 |
| 「端上不引 UI 库」 | ✅ 强化：现有多语义色板（涨红/跌绿/机会紫/龙金/预警青）与任何通用库的默认色板冲突，首期自研更省 |
| 后端不动 | ✅ 保留：仅新增 serve.py + 3 个只读接口 |
| L1 = serve.py | ✅ 保留，且现在是 F0 的前置 |
