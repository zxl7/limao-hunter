# 狸猫系统产品化 · 整体架构设计方案

> 版本：v1 草案 ｜ 日期：2026-09-14 ｜ 性质：**方案设计，不含实现代码**
> **已归档**：其中关于保留 HTML、双模及 `file://` 的建议已于 2026-09-29 失效；当前展示架构以终端 React 页面为准。
> 覆盖范围：模块拆解 · 功能模块 · 整体架构 · 技术选型与交付形态 · 部署结构
> 依据：对本机三套现有资产的实测盘点（文件级），非推测。

## 0. 结论速览（TL;DR）

| 决策项 | 结论 | 一句话理由 |
|---|---|---|
| 架构基准 | **以 quant-review 的分层规范为全系统基准** | 它是三套里唯一有「数据契约 + 模块 DAG + 可单测」的工程化结构 |
| 拆解范式 | **以大涨小程序的四层分离范式治理狸猫的脚本群** | 该范式已在生产验证：纯函数规则层可脱离云环境单测 |
| 架构形态 | **模块化单体（Modular Monolith）**，不做微服务 | 单人 + 少量客户的规模，微服务的分布式复杂度无收益 |
| 后端语言 | **Python / FastAPI 为主**（领域计算全在 Python） | 48.8k 行领域资产不重写；同语言免胶水 |
| 前端框架 | **Vue 3 + Vite + TS + ECharts + Pinia** | quant-review 已验证；用户主技术栈 |
| Element 采用 | **分区采用**：管理侧用 Element Plus，行情侧自研 + CSS Token | Element 是 B 端设计语言，用于高密度行情看板会「重且僵」 |
| 交付形态 | **Web 为主（多租户 URL）+ Tauri 桌面壳为可选补丁** | 发 URL 零交付成本；Tauri 满足「卖安装包」的客户心理且体积仅 ~5-10MB |
| 部署 | **B 档：单台轻量云服务器 + Docker Compose** | 实时可控、可多租户、可 WebSocket；A 档（纯静态托管）作降级路径 |
| 存储 | **PostgreSQL 为主 + Redis 缓存 + Parquet/对象存储归档** | JSON 按日落（现 97MB）无法支撑多租户并发查询 |
| 迁移策略 | **四期渐进，每期可独立上线且可回滚** | 严禁「推倒重写」，全部走双写 → 灰度 → 切换 |

**关键结论**：三套资产是**互补而非重叠**——狸猫提供「业务深度与实时性」，quant-review 提供「工程规范与线上通道」，大涨提供「交付形态与规则清晰度」。这正是整合的可行性基础。

### 1.3 五个核心矛盾（架构必须解决的）

1. **同一份数据被抓 N 遍，口径还不一致**
   全市场涨停池在狸猫（东财 + 选股宝）、大涨（同花顺）、quant-review（必盈）各抓一次；连「涨停」的判定散落在 `zt_genes._is_zt_row` / `feedback_matrix` / `board_core` 等多处。
   → 需**唯一采集网关 + 单一判定函数**（狸猫已有先例：`flow_noise.py` 是单一权威来源）。

2. **无统一数据契约**
   狸猫是「脚本各自解析 JSON、按日落地」；quant-review 已有 `Context{meta, raw, features, marketData}` 与模块 `requires/provides` DAG。
   → 以 quant-review 契约为基准统一，这是**投入产出比最高的一步**。

3. **调度与运行绑死本机**
   launchd 双守护 + 本机 Python 环境 + 本机 cache 97MB。客户无法使用，也无法水平扩展。
   → 需**采集与计算服务化**，本机降级为「兜底通道」（此双通道经验 quant-review 已有：Actions 主 + 本机 launchd 兜底）。

4. **前端三份、形态三种**（预渲染单文件 / 小程序 / SPA），入口不统一
   → 需**统一门户 + 统一组件层**，各形态退化为「同一份数据契约的不同渲染器」。

5. **客户通道只有一对一飞书 webhook**
   现有 `client_mirror` 是「1 个客户 = 1 个 webhook + 关键词白名单」，无法规模化、无法计量、无法设有效期。
   → 需**客户实体化 + URL 签发 + 内容包**。

## 2. 目标架构：三层五域

### 2.1 三层

```
┌─ L1 数据层 ───────────────────────────────────────────────┐
│  采集网关（唯一出网口）→ 归一化 → 契约校验 → 落库/落盘      │
│  职责：只取数，不做业务判断（对齐 quant-review 的 data 层）  │
├─ L2 领域层 ───────────────────────────────────────────────┤
│  纯函数/准纯函数计算：情绪 · 梯队 · 异动 · 选股 · 复盘       │
│  每个模块声明 requires / provides，输出对契约的 patch       │
├─ L3 交付层 ───────────────────────────────────────────────┤
│  统一门户（Web 主）· 小程序（副）· 桌面壳（可选）· 推送通道  │
│  渲染器只消费契约，不知道数据怎么来的                       │
└───────────────────────────────────────────────────────────┘
```

### 2.2 五域（功能域划分）

| 域 | 名称 | 覆盖能力 | 主要资产来源 |
|---|---|---|---|
| D1 | **短线情绪盘面综合域** | 短线看盘 · 资金流复盘 · 连板天梯 · 异动监管 | 狸猫 watch + quant-review 7 Tab + 大涨 4 页 |
| D2 | **选股与接力域** | 候选池 · 接力五维 · 竞价预期 · 净值账本 · AI 独立轨 | 狸猫 wealth_code 全部 |
| D3 | **客户与权限域** | 客户台账 · URL 签发 · 内容包 · 计量 · 有效期 | 狸猫 client_mirror（升级为表驱动） |
| D4 | **数据交互域** | 量化查询 API · 爬虫数据接入 · 实时快照 · WebSocket | laicai 雏形 + quant-review CLI |
| D5 | **平台治理域** | 调度 · 质量门 · 审计 · 回测自学习 · 备份 | 狸猫 system_health/quality_gate/backtest_engine |

**已识别的耦合点（拆解时优先处理）**：
1. `intraday_pulse.py` 2,044 行 / `live_signal.py` 2,396 行 —— 单文件承载「取数 + 计算 + 渲染 + 推送」四职责，须按层切分。
2. 「涨停判定」散落多处 → 收敛为单一函数（`flow_noise.py` 已是单一源范式）。
3. `HTML/gen_*.py` 内嵌 HTML 字符串 + 直接 `urllib` 出网 → 应拆为「数据准备」与「渲染」两段，出网归 M1。
4. 硬编码路径 `ROOT / "cache" / ...` 遍布 → 需统一路径解析模块。
5. `memory_lib.py` 承担跨任务共享状态 → 需升级为标准持久层（现在靠文件）。

### 3.2 大涨小程序 → 4 层归并（**保留其范式，不保留其部署**）

现有云函数 `anomaly` 的四层分离是**本系统最好的模块化样本**，直接映射：

| 现有层 | 文件 | 归并到 | 说明 |
|---|---|---|---|
| 访问层 | `ths.js` | **M1 采集网关** | 唯一出网、信封解析、超时重试 —— 保持「Key 只在服务端」原则 |
| 规则层 | `rules.js` | **D1 异动监管子模块** | 纯函数、可脱离环境单测 —— **此范式应反向推广到狸猫全部规则** |
| 存储层 | `store.js` | **统一数据层** | `anomaly_records` / `anomaly_runs` → PostgreSQL 表 |
| 分派层 | `index.js` | **D4 统一 API** 的一个路由组 | `list` / `detail` / `meta` / `rebuild` 保留接口语义 |

**注意**：小程序本身建议**保留为独立交付端**（微信内触达优势），但数据源从「直连同花顺」改为「调统一后端 API」，消除重复采集。其 `scope`（`severe`/`event`/`ladder`）服务端过滤设计值得在 Web 端复用。

### 3.3 quant-review → 升格为**全系统架构基准**

它已有的七层（`data → cache → features → metrics → modules → render → cli`）与三项机制，直接定为规范：

| 机制 | 现状 | 升级为全系统规范 |
|---|---|---|
| **Context 契约** | `{meta, raw, features, marketData}` | 扩展为 `MarketSnapshot`，三端共用 |
| **模块接口** | `name` / `requires` / `provides` / `compute(ctx)->patch` | 全部领域模块强制实现 |
| **DAG 拼装** | FULL 全跑 / PARTIAL 只跑目标 + 依赖链 | 支撑「客户按内容包订阅子集」 |
| **浅合并 patch** | 模块只覆盖自己的 key，禁止跨界 | 保证模块可独立重跑与替换 |

### 3.4 拆解四原则

1. **单一出网口**：只有 M1 采集网关可以访问外部数据源；领域层绝不 `requests.get`。
2. **契约先行**：模块之间只通过 `Context` 传递，禁止 cross-call 内部函数。
3. **可单测**：领域模块 `compute()` 必须是纯函数或准纯函数（IO 在 data/cache 层完成）——对标 `rules.js` 可 `node` 直接单测。
4. **可回滚**：每次模块边界调整保留可逆开关（沿用现有 `ENABLE_*` / `AUTO_APPLY` 惯例）。

## 4. 功能模块设计

### 4.1 短线情绪盘面综合模块（D1）

**定位**：一个模块组，四个子模块共享同一份 `MarketSnapshot`。

| 子模块 | 输入 | 输出（契约 key） | 资产来源 | 落地形态 |
|---|---|---|---|---|
| **① 短线看盘** | 指数 / 量能 / 涨跌家数 / 板块 / 自选 | `panorama` · `indexMini` · `sectorRank` · `watchlist` | 狸猫 `watch.html` 8 区布局（现为预渲染 + 30s fetch 双模） | 门户 Tab1，**保留双模**（HTTP 实时 / file:// 离线） |
| **② 资金流复盘** | 主力 / 超大 / 大单净流 + 板块聚合 | `capitalFlow{main,superLarge,large,bySector}` | 狸猫 `common/em_flow.py` + 已有设计 `config/design_资金流分层对接_CapitalPulse.md` | 门户 Tab2 上半区 |
| **③ 连板天梯** | 涨停池逐日 + 晋级统计 + 股性 | `ladder` · `promoteRate` · `ztGenes` · `boardCore` | 狸猫 `promo_quant` + `zt_genes` + `board_core`；quant-review `ladder` 模块；大涨 `pages/ladder` | 门户 Tab3 |
| **④ 异动监管** | 涨停 / 跌停 / 炸板池 + 偏离值 + 监管红线 | `anomaly{severe,event,records}` · `regulatoryRedline` | 大涨 `rules.js` 四档口径（最完整）；狸猫 `regulatory_watch` | 门户 Tab4 |

**④ 的关键决策**：异动口径统一采用**大涨的四档标准**（① 一般异常 ±20% / ② 10 日 ≥+100% / ③ 10 日内 3 次同向 / ④ 30 日 ≥+200%），因其已用 2026-09-11 真实数据比对验证（7/8 只对齐），且阈值与基准映射集中在常量表。狸猫的监管红线作为「**第五档：行政监管信号**」叠加（上交所出手、账户暂停等），二者互补不冲突。

### 4.2 客户管理模块（D3）

**现状**：`config/settings.json` 的 `client_mirror` — 1 客户 = 1 webhook + `card_patterns` + `title_patterns` + `exclude_patterns`，一对一、文件配置。

**目标**：升级为**表驱动的客户实体 + URL 签发**。

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `clients` | `id` · `name` · `slug` · `status` · `expires_at` | 客户主档 |
| `client_channels` | `client_id` · `type`(`url`\|`webhook`\|`wechat_mp`) · `target` · `secret_hash` | 交付通道（一客户可多通道） |
| `content_packs` | `id` · `name` · `rules`（模块白名单 + 时效） | 内容包 = 订阅哪些模块 |
| `client_subscriptions` | `client_id` · `pack_id` · `start` · `end` | 订阅关系 + 有效期 |
| `access_logs` | `client_id` · `ts` · `path` · `ip` · `ua` | 计量与审计 |

**URL 签发形态**（两种，按客户类型选）：

| 形态 | 链接形式 | 适用 | 优劣 |
|---|---|---|---|
| **动态门户** | `https://<domain>/c/<slug>?t=<token>` | 需实时数据、需计量 | 优：实时、可随时改内容、可计量；劣：需服务器与鉴权 |
| **静态快照** | `https://<domain>/s/<slug>/<date>/` | 只需每日盘后交付 | 优：零后端压力、可 CDN、可归档；劣：非实时 |

**内容包设计**：直接复用现有 `client_mirror` 的白名单语义（如「短线精灵 + 盘中快照 + 复盘卡」，机构卡永久排除），迁移为 `content_packs.rules` 的 JSON 字段 —— **零概念变更，仅载体升级**。

### 4.3 数据交互模块（D4）

**定位**：全系统唯一的数据出口，对齐领域层与交付层。

```
外部数据源 ──▶ M1 采集网关 ──▶ 归一化 + 契约校验 ──▶ 存储（PG/Redis/对象存储）
                                                        │
                        ┌───────────────────────────────┤
                        ▼                               ▼
              D4 API 网关 (REST/WS)              L2 领域模块（内部调用）
                        │
        ┌───────────────┼───────────────┬──────────────┐
        ▼               ▼               ▼              ▼
   门户 SPA        小程序          桌面壳        客户专属 URL
```

**接口分组**：

| 分组 | 路由前缀 | 内容 | 来源 |
|---|---|---|---|
| 量化查询 | `/api/v1/query/*` | 行情 / 涨跌停状态 / 股池 / 个股详情 | laicai 雏形（`/quote`、`/limit-status`）+ 狸猫 pipeline 产物 |
| 爬虫数据 | `/api/v1/raw/*` | 快讯 / 龙虎榜 / 研报 / 资金流原始 | `crawler/` 采集器（`hithink_fetch` `lhb_fetch` `newsflash_express`） |
| 市场快照 | `/api/v1/snapshot/*` | 当日 / 历史 `MarketSnapshot` | quant-review pipeline 产物 |
| 实时推送 | `WS /ws/v1/stream` | 指数 / 异动 / 精灵增量 | 狸猫 30s 守护循环服务化 |
| 客户侧 | `/api/v1/client/*` | 鉴权 · 内容包 · 计量 | D3 |
| 管理侧 | `/api/v1/admin/*` | 客户 CRUD · 任务台账 · 配置 | D3 + D5 |

**契约基准（统一 `MarketSnapshot`）**：

```
MarketSnapshot
├── meta        { date, generatedAt, ruleVersion, source[] }
├── raw         { pools{zt,dt,zb,qsgc}, index, themes }        ← 原始，只增不改
├── features    { mood_inputs, ladder_inputs, theme_inputs }   ← 可重算、可落盘
├── marketData  { panorama, capitalFlow, ladder, anomaly, ... }← 渲染契约，模块 patch
└── audit       { caliber, warnings[], degraded[] }            ← 诚实降级标注
```

**「诚实降级」原则沿用**：数据源失效时标 `degraded` 而非静默填默认值（现有 `push2 → push2delay` 降级逻辑已体现此原则）。

| **V4 财富密码** | 候选 / 接力 / 竞价验证 / 净值战绩 | 狸猫 `wealth_code` |

### 5.2 多端复用策略

**核心原则：一份数据契约，多个渲染器。**

```
                    MarketSnapshot（唯一契约）
                             │
     ┌───────────┬───────────┼───────────┬───────────┐
     ▼           ▼           ▼           ▼           ▼
  门户 SPA    小程序      桌面壳    飞书卡片    静态快照
 (Vue3)   (原生/Taro)   (Tauri)   (现有)     (singlefile)
```

- **门户 SPA**：主力，`Vue 3 + Vite`，可 `vite-plugin-singlefile` 打成单 HTML（**保留现有 file:// 双击即看的离线能力**）。
- **小程序**：保留大涨现状，数据源改调统一 API；或长期用 Taro 与门户共享组件层。
- **桌面壳**：Tauri 2 套壳指向自家域名（见 §7）。
- **飞书卡片**：现有 `push_card.py` + 模板体系**完整保留**，作为「主动触达」通道 —— 这是狸猫的核心竞争力，不应被 Web 替代。
- **静态快照**：客户归档交付，直接复用现有 `gen_*.py` 预渲染管线。

**关键保留项**：狸猫 `HTML/gen_watch.py` 已是「生成时内嵌数据 + HTTP 下 30s fetch 增量刷新」的**双模设计**，这是三套资产里最被低估的工程资产 —— 它同时满足「离线可看」与「在线实时」，迁移时必须保留此特性。

## 6. 技术选型

### 6.1 前端

| 项 | 推荐 | 理由 | 备选 |
|---|---|---|---|
| 框架 | **Vue 3 + Vite + TypeScript** | quant-review 已验证（`useMarketData.ts` + `types/`）；用户主技术栈 | React（无必要切换） |
| 状态 | **Pinia** | 用户已熟；多视图共享快照 | — |
| 图表 | **ECharts 5** | quant-review 已用；行情图表生态最全（K 线 / 分时 / 热力 / 关系图） | — |
| 打包 | **Vite + `vite-plugin-singlefile`** | 保留单文件离线能力 | — |
| 样式 | **CSS 变量 Token**（沿用现有 `:root`） | 狸猫已有 `--up/--down/--rec/--lead/--warn` 语义色板；改主题只动一处 | UnoCSS / Tailwind（可选叠加） |

#### Element 采用评估（用户明确提出）

**结论：分区采用，不做全局统一 UI 库。**

| 维度 | 分析 |
|---|---|
| Element Plus 的设计定位 | B 端后台管理系统：表格 / 表单 / 弹窗 / 树 / 分页。设计语言偏「宽松留白 + 标准组件」 |
| 行情侧需求 | **高信息密度**（单屏 40+ 数据点）、**实时刷新**（30s）、**弱交互**（看为主）、**双主题**、**自定义语义色**（涨红跌绿） |
| 冲突点 | Element 的表格行高、间距、默认色板与「行情软件感」冲突；深度覆盖需大量 `!important`，维护成本高于自研 |
| 适配点 | 管理侧（V6 管理台）**完全契合**：客户 CRUD 表格、内容包配置表单、任务台账、弹窗 |
| 现有证据 | quant-review 已自研 `TabBar` / `HeroSection` 未用 UI 库；狸猫 HTML 全手写 CSS —— 说明行情侧的既有选择就是「自研」 |

**推荐落法**：

```
门户前端
├── 行情侧（V1–V5）  → 自研组件 + ECharts + CSS Token     【不引入 Element】
└── 管理侧（V6）     → Element Plus（按需引入）            【引入 Element】

约束：两者共享 Token 层，Element 主题通过 CSS 变量覆写到同一色板；
     禁止在行情侧引入 Element 组件（防设计语言串味）。
```

**若倾向「单一 UI 库」**：则建议 Naive UI（主题变量体系更贴近自定义需求）而非 Element Plus；但仍不推荐在行情侧使用任何通用 UI 库。

### 6.2 后端

| 方案 | 描述 | 评价 |
|---|---|---|
| **A. FastAPI 模块化单体** ⭐ | 采集 + 领域 + API 同进程，按 §3 目录边界隔离 | **推荐**：领域计算全在 Python，零胶水；`laicai` 已验证可行 |
| B. Node(NestJS) API + Python 计算 | 双语言，靠 HTTP/队列通信 | 弃：多一层胶水与序列化开销，规模不匹配 |
| C. 微服务 | 采集 / 计算 / API 独立部署 | 弃：单人 + 少量客户规模下，分布式复杂度无收益 |

**关键辨析**：**「模块化单体」不等于「不拆模块」**。模块边界靠 **目录 + 契约 + 依赖规则** 强制，而非进程与网络。这样既拿到清晰的模块化收益，又避免分布式事务、服务发现、链路追踪等无谓成本。若未来某模块确需独立（如采集需高频扩缩容），可单独抽出 —— 拆解成本被目录边界预先降低。

**后端技术栈**：

| 层 | 选型 |
|---|---|
| Web 框架 | FastAPI + Uvicorn |
| 数据访问 | SQLAlchemy 2.x（异步）+ Alembic 迁移 |
| 任务调度 | APScheduler（进程内）→ 未来可换 Celery/RQ |
| 校验 | Pydantic v2（契约即模型，天然校验 `MarketSnapshot`） |
| 鉴权 | JWT + 客户 token（哈希存储） |
| 实时 | FastAPI WebSocket |

### 6.3 数据存储

| 用途 | 选型 | 理由 |
|---|---|---|
| 业务主库 | **PostgreSQL** | 多租户、并发查询、JSONB 存 `MarketSnapshot`、时序扩展可选 |
| 热缓存 | **Redis** | 实时快照、去重窗口（现有 `dedup_window_min`）、限流 |
| 历史归档 | **Parquet + 对象存储（S3/OSS/COS）** | 冷数据压缩比高、按日分区裁剪 |
| 本地分析 | **DuckDB**（可选） | 全市场截面因子分析（TSP 借鉴文档已论证该路径） |

**迁移策略：双写**。
`cache/*.json` 按日落 → 继续写（不破坏现有 48.8k 行链路），同时写 PG；读路径灰度切换。**先写后读，验证后再切**。

> 参考：现有 `cache/` 97MB / 1,977 文件，JSON 按日落形态在「单人单机」下够用，但**无法支撑多客户并发查询与内容包按需过滤** —— 这是必须引入 PG 的根因。

### 6.4 调度

| 层 | 选型 | 说明 |
|---|---|---|
| 主通道 | **服务器端 APScheduler / cron** | 替代 launchd，进程内可观测 |
| 兜底通道 | **保留本机 launchd 双守护** | 沿用「主 + 兜底」经验（quant-review 已是 Actions 主 + launchd 兜底） |
| 交易守卫 | 保留现有「交易日探针 + 秒退」机制 | 三套资产均已踩过交易日历的坑 |

**调度铁律保留**：平台限制结论（`MINUTELY` 不支持、`HOURLY` 忽略 `BYHOUR/BYMINUTE`、盘中任务统一用 `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR`、触发抖动 ±3~9 分需 prompt 步骤 0 交易守卫秒退）—— 服务化后仍然适用。

## 7. 交付形态对比与推荐

### 7.1 网页 vs 本地客户端（安装包）

| 维度 | 网页（SaaS / 多租户 URL） | 本地客户端（安装包） |
|---|---|---|
| **交付成本** | 极低（发一个 URL） | 高（打包 / 分发 / 引导安装） |
| **更新** | 即时（刷新即最新） | 需重新分发或内置自动更新 |
| **数据位置** | 云端（需隔离与合规） | 本地（客户心理更安全） |
| **环境依赖** | 仅浏览器 | 需适配 macOS / Windows / 架构 |
| **离线能力** | 弱（可 PWA 局部缓存） | 强（天然离线） |
| **计算能力** | 受服务端资源约束 | 可用客户本机算力 |
| **反编译风险** | 低 | **高**（前端逻辑可被逆向） |
| **计量与风控** | 强（服务端可控、可封禁） | 弱（发出即失控） |
| **实时性** | 强（WebSocket） | 中（需自己连服务端） |
| **客户感知** | 「订阅服务」 | 「买了个软件」 |
| **运维负担** | 服务端集中运维 | 分散（客户环境千差万别） |

### 7.2 推荐方案：**Web 为主 + Tauri 壳可选**

**理由（基于本项目特性）**：

1. 本系统的**核心价值在数据与算法**（情绪 / 梯队 / 异动 / 选股），不在客户端能力 —— 数据必须留在可控侧，否则 `content_packs` 内容包与计量体系全部失效。
2. 现有资产已高度适配 Web：quant-review 已在 Pages 上线，狸猫 HTML 已是单文件可离线 —— **Web 迁移成本最低**。
3. 「客户要求安装包」的真实诉求通常是 **桌面图标 + 独立窗口 + 本地留存感**，而非技术必需 —— Tauri 壳可低成本同时满足两者。

| 形态 | 推荐度 | 适用场景 |
|---|---|---|
| **Web（多租户 URL）** | ⭐ 主推 | 所有客户的标准交付 |
| **Tauri 2 桌面壳** | ⭐ 可选补丁 | 客户明确要「安装包」体验时；同一套前端代码套壳指向自家域名 |
| **本地化部署包**（Docker Compose） | ⭐ 企业版 | 客户要求数据不出内网时，交付整套后端 |
| Electron | ✗ 不推荐 | 体积 150MB+、内存占用高、macOS 签名公证繁琐 |
| 纯离线单文件 HTML | ⭐ 保留 | 现有 `gen_*.py` 预渲染管线，客户归档交付 |

**Tauri 选型理由**：体积约 5–10MB（vs Electron 150MB+），Rust 内核，macOS/Windows/Linux 均支持，与「单文件 HTML 前端」天然契合。用户环境为 macOS arm64 + Node 22 + pnpm，工具链匹配。

## 9. 迁移路线图（四期）

> 原则：**每期独立上线、独立可回滚，不做推倒重写**。

| 期 | 主题 | 关键动作 | 验收标准 |
|---|---|---|---|
| **P1 · 契约与拆分** | 先立规矩，不动生产 | ① 定义 `MarketSnapshot` 契约（以 quant-review Context 为基准）② 收敛「涨停判定」为单一函数 ③ `intraday_pulse.py` / `live_signal.py` 按层切分 ④ 建立 `packages/contracts` | 契约校验 100% 通过；现有链路行为零变化（回归测试全绿） |
| **P2 · 数据层服务化** | 双写 + 灰度读 | ① 建 PG 库表 + 采集 worker ② `cache/*.json` 与 PG **双写** ③ 读路径灰度切 PG ④ 采集网关抽为独立服务 | 双写一致性校验通过；切读后卡片内容与旧链路逐字节一致 |
| **P3 · 门户与客户域** | 统一入口 + 客户 URL | ① 门户 SPA 上线 V1–V4（迁 watch.html / quant-review 7Tab / 大涨 4 页）② 客户管理模块落库 ③ `client_mirror` 升级为表驱动 ④ URL 签发上线 | 门户可替代旧页面；老客户迁移到 URL 后内容包无损 |
| **P4 · 管理台与交付** | 产品化收口 | ① 管理台 V6（Element Plus 区）② 私有部署包（compose）③ Tauri 壳 ④ 小程序切统一 API | 一条命令可起完整环境；客户可自助 |

**优先级判断依据**：P1 无用户感知但决定后续所有成本（契约是复利资产）；P2 解决「绑死本机」根因；P3 是用户价值兑现点；P4 是商业化收口。

## 10. 风险与待决事项

### 10.1 已识别风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **口径漂移**（四处「涨停判定」） | 数据不一致，客户可见矛盾 | P1 收敛为单一函数 + 契约测试守门 |
| **双写期数据不一致** | 静默错数据（最危险） | 一致性校验脚本 + 差异告警，不达标不切读 |
| **微信小程序类目限制** | 大涨小程序无法正式发布（个人主体拿不到《增值电信业务经营许可证》） | 定位为**体验版自用端**；商业化走 Web（无类目限制） |
| **数据源合规** | 东财/同花顺/必盈等接口授权风险 | `marketData.meta.source[]` 全链路标注；私有部署包交由客户自担数据源 |
| **单机单点故障** | B 档服务器宕机即全停 | launchd 双守护兜底 + 每日 tar.gz 备份（已有 `backup_snapshot.py`） |
| **前端逻辑可逆向** | 客户拿到 Tauri 包可逆向算法 | 核心算法**只在服务端**，客户端不落策略逻辑 |
