# 调度分层与模块拆分方案（2026-10-30）

> 依据：现有 25 个自动化 + 5 个 launchd + 1 条 cron 的实际运行数据，以及服务器实测（2C/1.9G，数据链单次 3s）。
> 目标：**把「取数与派生」沉到服务器高频跑，把「判断与决策」收回本地按天批量**。

---

## 一、分层依据：按性质切，不按重要性切

四条判据，任一命中即归入对应层：

| 判据 | 含义 | 命中后归属 |
|---|---|---|
| **幂等性** | 同一输入重跑结果一致，可安全重放 | 实时模块（服务器） |
| **状态依赖** | 需要本机会话 / 持仓 / 自选 / prompt 版本 | 智能模块（本地） |
| **延迟敏感度** | 秒级失效（行情、封单、竞价） | 实时模块 |
| **失败代价** | 失败可自动补齐 vs 需人工重判（烧 token） | 前者实时，后者日批 |

补充一条工程约束：**产生数据的一方负责落盘，消费数据的一方只读**。这条决定了单向数据流，杜绝双写。

---

## 二、模块划分

### M1 实时模块（服务器，常驻 + 高频）

| 任务 | 频率 | 依赖 | 现状 |
|---|---|---|---|
| `pulse_fetcher.sh` 主链（10 子步骤） | 交易时段 30s / 午休 5min / 非交易 10min | 东财、腾讯、同花顺 HTTP | Mac cron 每分钟（脚本自节流） |
| `realtime_push_pipeline.py` 规则卡 | 同上拍 | 上一步产物 | 同链 |
| `link_guard.py` 链路断档守卫 | 同拍 | `data_ready.json` | 同链 |
| 题材 / 概念快照 `hithink_fetch` | 5–15min | 同花顺题材接口 | 随链或独立 |
| 板块资金 `sector_fund_pool` | 1–5min | 东财资金流 | 随链 |
| 龙虎榜 `lhb_fetch` | 每日 17:00（披露制） | 同花顺榜单 | 盘后一次 |
| `serve.py` 站点 | 常驻 | 本地 JSON | 已在服务器 |

**为什么整条链都上去**：它只做「取 → 算 → 存」，全部幂等；单次实测 **3s**，30–60s 一拍对 2 核机器是 5% 占用；且它不产生任何需要人工判断的内容。

### M2 日批模块（服务器，盘后定时）

| 任务 | 时点 | 依赖 | 说明 |
|---|---|---|---|
| `capture_daily.py` 日终落盘 | 15:05–15:30 | 当日行情 | 决定次日可复算的基准 |
| `guard_eod_chain.py` 落盘守护 | 17:30–17:50 | 上一步产物 | 缺件重跑 |
| 股性库重建（`zt_genes`） | 盘后一次 | 涨停历史 + K 线 | 1607 个 JSON |
| 指标派生（晋级率/反馈矩阵归档） | 盘后 | 日终数据 | 无 AI，可回放验证 |

### M3 智能模块（本机，按天/按需）

| 任务 | 现频率 | 建议 | 依赖（本地） |
|---|---|---|---|
| 盘前预测 06:06 | 每交易日 1 次 | **保留**，读服务器镜像 | prompt、自选池、模型 |
| 机构题材热度 07:15 | 1 次 | **保留** | 机构数据 + 参数 |
| 竞价验证 09:25 + 哨兵 09:28 | 1 次 | **保留**（竞价不可回放） | 竞价快照 + 参数 |
| 盘中猎手 ×10（09:30–14:45） | **10 次/日** | ⛔ **合并为 1 次**（收盘后批量），或改「事件触发」 | 持仓、自选、模型 |
| 尾盘潜伏卡 14:30 / 买价 14:50 | 2 次 | 卡**保留时点**（吃单必须当日），AI 研判改盘后复盘一次 | 持仓、成本 |
| 接力卡 15:30 | 1 次 | 保留 | 参数 |
| 盘后复盘 17:18 | 1 次 | 保留（已成主力产出） | 全量数据 |
| 推测回测 17:50 / 周五优化 | 1 次 | 保留 | 本地回测库 |
| 尾盘结算 次日 10:00 | 1 次 | **保留**（交易动作） | 持仓账本 |

**关键收缩：盘中 AI 卡从 10 次/日 → 1 次/日（或事件触发）**。这是本方案里唯一大幅改变体验的地方，理由见第四节。

### M4 本地交互（保留在 Mac，不上服务器）

- 持仓账本 / 成本价 / 自选池：**唯一真源在本机**，服务器不需要也不该有。
- 公众号文案、复盘成文：涉及人设与措辞，非自动化产物。
- 竞价哨兵（launchd，09:28）：只判日志并告警，与交易时段强绑定，留在本机更稳。

## 三、依赖关系

```
        ┌──────────── M1 实时（服务器 30–60s）────────────┐
        │ 三方接口 ─▶ 采集 ─▶ 聚合 ─▶ 指标 ─┬─▶ 站点 JSON │
        │                                  └─▶ 规则卡（飞书）│
        └───────────────────┬───────────────────────────┘
                            │ 落盘
                    ┌───────▼────────┐
                    │ M2 日批（盘后） │ 日终 / 股性 / 归档
                    └───────┬────────┘
                            │ 单向镜像（服务器 → 本机）
        ┌───────────────────▼───────────────────────────┐
        │ M3 智能（本机，读本地镜像）                    │
        │ 盘前 1 次 · 竞价 1 次 · 盘后 1 次（+ 事件触发）│
        └───────────────────┬───────────────────────────┘
                            │ 读本地参数
                    ┌───────▼────────┐
                    │ M4 本地真源     │ 持仓 / 自选 / prompt
                    └────────────────┘
```

三条硬约束：
1. **数据只往下流**（M1 → M2 → M3），不允许 M3 回写 M1 的落盘目录。
2. **M3 不直接读服务器 HTTP**，读本地镜像（`mirror_back.sh`），这样 AI 脚本零改造。
3. **镜像必须先于 AI 任务**：盘前 06:06 的任务要求镜像在 06:00 前完成一次。

## 四、评估

### 4.1 时效性

| 环节 | 现状 | 方案后 |
|---|---|---|
| 行情到站 | 30–90s（Mac 采集 + 本机同步） | **30–60s**（同机，少一跳网络） |
| 规则卡（事实播报） | 60s 内 | **30–60s** |
| AI 判断卡 | 盘中每 30–60 分钟 | **无盘中 AI 卡** |

代价必须说清：盘中不再有「AI 解读」。替代是两个：
- 规则卡负责**事实**（谁涨停、封单多少、板块几连），本来就是确定性输出；
- AI 改为**收盘后批量**，输出「今日决策质量 + 次日预案」，而这件事本来更适合盘后做。

真要在盘中要 AI，用**事件触发**而不是定时：服务器在 `signals.json` 里写入 `critical`（如涨停潮/跌停潮/冰点解冻），Mac 收到后跑一次。成本只在真正需要时发生。

### 4.2 资源消耗

| 资源 | 实测/估算 | 判断 |
|---|---|---|
| 服务器 CPU | 实时链单次 3s / 60s ≈ **5% 单核**；峰值并发 2 个 python | 2 核实测无压力 |
| 服务器内存 | 采集进程约 100–150M；`serve` 常驻 ~50M；可用 950M | 安全，但**不建议再装 docker/node** |
| 磁盘 | release 56M + shadow 3.6M，日增 < 20M（股性/日终） | 22G 可用，够跑 2 年+ |
| 网络 | 30–60s 一拍，单次 2–4MB | 机房带宽远富余 |
| **本机** | 从「24h 待命 + 20 个 AI 时点」→「3–4 个时点 + 镜像拉取」 | **显著下降**（fan、电、token） |

按 token 粗算：10 个盘中猎手改成 1 次盘后，**AI 调用次数下降约 80%**。

### 4.3 稳定性

**变好的部分**
- 采集从「家用网络 + 睡眠/断电/合盖」→ 机房 7×24（已连续运行 228 天）。
- 失败可自动重试：`systemd Restart=always` + 脚本内 mkdir 锁 + 断档守卫。
- 版本可回滚：`releases/<stamp>` + `current` 软链，1 秒切回。

**变差的部分**
- **单点从 Mac 转移到服务器**：机器挂了整条链停。缓解：每日心跳卡 + 外部监控（Uptime 类）告警。
- **机房 IP 可能被数据源风控**：这是最大未知，家宽 IP 与云机房 IP 在东财/同花顺的判定不同，高频请求可能触发限流甚至验证码。必须影子期统计**成功率**，不能只看「能跑通」。

## 五、风险清单

| 风险 | 等级 | 触发条件 | 缓解 |
|---|---|---|---|
| 机房 IP 被风控 | **高** | 高频请求触发限流/验证码 | 影子期统计 3 日成功率；失败即加 UA/间隔退避；保留家宽为兜底源 |
| 双写 / 双推 | **高** | 迁移期间两边都跑 | 单向接管：切服务器时必须停本机 cron + 停正向 sync |
| 盘中无 AI 兜底 | 中 | 极端行情（跌停潮） | 规则卡加「极端事件」硬阈值告警；事件触发通道保留 |
| 本地参数漂移 | 中 | 持仓变更后 AI 仍按旧账本算 | 账本变更即打时间戳，AI 任务读前校验 `updated_at` |
| 镜像时序错位 | 中 | 镜像晚于 AI 任务 | 盘前镜像提前到 05:50；AI 任务先校验快照 ts |
| 卡片双通道打脸 | 中 | 规则卡与 AI 卡对同一票结论相反 | 卡片加 `source=rule|ai`；AI 卡不重复播报事实 |
| 交易日历双源 | 低 | 服务器 py3.12 与 Mac py3.13 版本差异 | 共用同一份 `config/` + 唯一源 `common/trading_calendar` |

## 六、可优化点

1. **信号驱动替代定时 AI**（收益最大）：把 AI 触发条件写成 `signals.json` 的字段，Mac 只在命中时跑。省 80% token，且比定时更贴盘面。
2. **卡片去重 ID**：`{date}-{type}-{key}`，两通道共用，前端/飞书侧按 ID 幂等。
3. **股性库按需加载**：`zt_genes` 1607 文件（81M，压缩后仍占包大头），改前端按代码请求，可再省 20M 传输并减少同步时间。
4. **采集多源兜底**：东财失败自动退腾讯/新浪，把「单源失败」从故障降级为抖动。
5. **每日心跳卡**：服务器每天 08:55 推一张「采集成功率 / 数据新鲜度 / 磁盘」自检，替代「等用户发现」。
6. **本机只做判断**：长期看 Mac 上不该再有任何「取数」代码，只有参数 + 模型调用，关机即暂停判断但数据不断。

## 七、实施顺序建议

| 阶段 | 动作 | 验收 |
|---|---|---|
| P0（已做） | 站点 + 数据镜像上线 | `verify.sh` 10/10 |
| P1 | 影子跑采集 3 日，统计成功率与 IP 风险 | 成功率 ≥99%，无验证码 |
| P2 | 服务器接管 M1，本机停 cron + 停正向 sync | 站点自给自足，Mac 关机数据仍新 |
| P3 | 本机改 `mirror_back` 只读消费 | AI 脚本零改造跑通 |
| P4 | 盘中 AI ×10 合并为盘后 1 次 + 事件触发 | 对比 1 周，确认判断质量未下降 |
| P5 | 日批链路（M2）迁服务器 | 日终文件齐全率 100% |

## 八、本地落地物（2026-10-30 已建）

| 文件 | 作用 |
|---|---|
| `config/schedule_layers.json` | **唯一分层真源**：31 个任务的层归属、触发方式、频率、依赖、可迁性、动作（keep/merge） |
| `scripts/schedule_audit.py` | 体检：依赖是否成环、实际在跑的有没有漏登记、待收敛任务是否还在跑、探活 cron/launchd |
| `scripts/layer_run.sh` | 单层手动执行：`plan` 看窗口 / `M1` 只产数据 / `M1 --push` 连卡 / `M2` 日批 dry-run |

**分层现状（实测）**：M1 7 个 · M2 4 个 · M3 17 个 · M4 3 个；可迁 10、不外迁 21。
依赖图**无环、无悬空引用**；cron 主链与 5 个 launchd 全部在册。

**待收敛**：盘中猎手 10 个时点仍按原计划在跑（`action=merge`）。暂不停，等确认后一次性暂停；
`schedule_audit.py` 会打印 10 个 automation id，便于批量 PAUSED。

**边界确认（用户 2026-10-30）**：凡涉及本机定时的任务一律不外迁；Mac 未开机时这些时点
**直接跳过即视为正常**，不做服务器降级版。

**本地观察的正确用法**
```bash
python3 scripts/schedule_audit.py          # 分层是否自洽、有没有该停没停
bash scripts/layer_run.sh plan             # 现在处于哪层窗口
bash scripts/layer_run.sh M1               # 单跑实时数据面（不推送）
bash scripts/layer_run.sh M2               # 日批 dry-run，看清将执行什么
```
